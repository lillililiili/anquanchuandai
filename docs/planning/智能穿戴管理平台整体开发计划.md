# 智能穿戴管理平台整体开发计划

版本：V1.0　代码基线：2026-09-08　团队：2 人，AI 辅助开发

分工更新：现已确定你负责后端与 PC、协作者 B 负责 Android。具体执行顺序、责任和工作量以[后端与 PC 管理端分阶段详细开发计划](<E:/沉积岩/anquanchuandai/docs/planning/后端与PC管理端分阶段详细开发计划.md>)为准；本文原人员分配和阶段排期保留为早期规划参考，不再作为当前执行承诺。

本计划面向山东融瓴智能制造有限公司的电厂智能穿戴业务。目标是在现有安全帽系统基础上，形成能够管理多类穿戴装备、关联作业人员、发现现场异常并完成处置追溯的平台。首个交付重点是一个厂站内安全帽与安全带的真实业务闭环，随后逐步扩展电厂作业监护和多厂站运营。

建议采用“通用业务模型重新设计、现有技术和可验证组件渐进复用”的路线。两人团队先集中开发 PC 值班台和服务端，App 在同一接口契约下补充现场接警、查询和通信。暂不拆微服务，不同时重写三端，不以堆积页面或更换名称衡量完成度。

## 1 项目结论和交付目标

### 1.1 产品定位

对外名称统一为“智能穿戴管理平台”，保留融瓴品牌。平台服务于电厂现场的“人员—装备—区域—作业—事件—处置”全过程。

值班人员打开系统应能回答五个问题：谁正在什么地方作业；他携带了哪些装备；当前信息是否可信；有哪些异常需要处理；谁已经接手、处理到了哪一步。

设备管理员则需要知道装备是否在库、发给了谁、是否待检或维修、何时归还。安全管理人员需要知道哪些异常反复发生、哪些责任未落实、证据是否完整。三类需求共同构成平台，不能只围绕视频和地图设计。

### 1.2 首版成功标准

一名作业人员领取一顶安全帽和一条安全带，关联一个作业任务；真实设备产生协议支持的异常；系统按发生时间找到当时的人员和厂站；授权值班员收到事件并原子认领；通过可用通信渠道联系现场；提交处置和复核记录；归还设备后，历史人员、位置和证据保持不变。

通信失败、设备断网、定位未知、重复上报、人员换绑和两人同时认领，都必须有可解释的结果。没有可靠的挂钩或定位数据时，显示未知或待核实，不能显示“安全”“已挂好”或自动编造楼层。

### 1.3 按两人团队估算的时间窗口

以下是规划估算，不是已经验证的交付承诺。以两人全职、有至少一人能负责后端和数据库、硬件厂商配合为前提，从项目启动周起计算。

| 交付层级 | 建议窗口 | 实际交付内容 |
| --- | --- | --- |
| 可评审版本 | 第 4—6 周 | 通用人员和设备台账、领还、事件工作台；协议模拟数据清楚标识；可讨论真实业务流程 |
| 单厂真实设备试点 | 第 12—16 周 | 帽和带真实接入、接警处置、最低可用通信、任务关联、厂站权限及试点部署 |
| 首个生产候选版本 | 第 20—24 周 | App 核心流程、运行加固、备份恢复、现场连续运行、误报复核、部署和回滚验收 |
| 产品化扩展 | 首厂验收后滚动安排 | 第二厂站复制、气体设备、工作票对接、分层定位增强、设备运维与分析 |

没有安全带协议或样机时，第 12—16 周只能交付“安全帽试点加安全带模拟联调”，不能称为多品类真实设备验收。两人兼职、均不熟悉现有技术栈或同时承担硬件研发时，以上排期需要按有效投入重新估算。

## 2 文档和代码的实际基线

### 2.1 文档之间需要统一的决策

| 材料 | 可以继承的内容 | 本计划的调整 |

| 整体设计方案 DOCX | 以人为中心、能力驱动、一套告警中心、轻量分层厂区、品牌方向 | 不直接执行“不复用脚手架”；一期不同时承诺气体设备和所有厂型真实上线；基础账号权限提前 |

| 多品类平台方向 | 型号能力、佩戴历史、发生时关联、数据新鲜度和适配层 | 作为本次领域模型的主要输入，能力必须回到真实协议核实 |
| 台账验收记录 | 事务、版本冲突、厂站授权、领还、审计和重启验证的验收案例 | 当前仓库未找到对应通用台账实现和部署目录；作为可找回资产及验收模板，不计为本仓库已完成 |

### 2.3 复用策略

| 范围 | 建议处理 | 原因 |
| --- | --- | --- |
| 现有 Java 和 MySQL 技术路线 | 保留，做模块边界和工具链治理 | 两人可以集中在业务正确性；不用支付全面换栈成本 |
| 登录、角色、组织、字典 | 审查后复用 | 已有框架能力，但必须补业务对象权限和敏感字段验证 |
| 第三方安全帽接口 | 封装为 HelmetAdapter | 可利用协议知识，隔离旧帽号、凭证和回调格式 |
| PC 通用表格、弹窗、地图和播放器 | 按功能验证后复用，逐页迁移 | 可减少重复劳动，不直接复制帽子业务模型 |
| Flutter 数据、轨迹和 RTC 代码 | 保留技术基础，改成通用 API | App 有实际投入，重新开发不利于两人交付 |
| 旧帽表和历史记录 | 保留映射和只读回查入口 | 新旧数据可核对、可追溯，避免一次性全库改名 |
| 演示兼容、签到、AI 宠物等 | 独立演示环境或关闭产品入口 | 不计入首版安全闭环和真实业务完成度 |
| 后端附带 ruoyi-ui | 先核实部署用途，非主端则封存 | 避免维护两个 PC 前端，不直接删除未知现场依赖 |

## 3 电厂业务范围和优先级

### 3.1 一期必须完成的业务

| 模块 | 首期最小范围 | 验收重点 |
| --- | --- | --- |
| 厂站与人员 | 厂站、区域、组织、班组、承包商、人员有效期；人员与登录账号分离 | 没有账号的现场人员也能领装备；普通账号只能看授权范围 |
| 装备台账 | 型号能力、设备登记、分配厂站、领用归还、维修停用、历史 | 一人多设备；一台设备同一时间仅一个有效领用人 |
| 设备接入 | 一款安全帽、一款安全带；真实协议适配、身份校验、去重和异常隔离 | 真实报文可复现；模拟接入不得混入生产数据 |
| 可信状态 | 在线状态、最后上报、数据新鲜度、传感器异常、网关关系 | 新建资产不自动在线；网关在线不代表子设备在线 |
| 安全事件 | 统一事件编号、认领、处置、复核、关闭、升级和值班交接 | 并发认领互斥；事件关闭不能只改一项布尔字段 |
| 最小作业关联 | 任务、区域、时间、参与人、负责人、监护人、票号引用 | 告警可以还原当时作业；不开发完整电子两票审批 |
| 找人与通信 | 二维位置、来源和时间；单人联系、SOS；试点需要的 TTS | 真实接通才显示接通；失败可查，可人工改用其他渠道 |
| 运行保障 | 权限、日志、备份、重启恢复、部署脚本、基础健康监控 | 一台新环境可安装；备份可恢复；授权撤销能生效 |

首期试点部署一座厂站，但自动化权限测试必须至少有两个厂站，提前验证跨站隔离。第二种厂型可以先用明确标识的配置样例验证可扩展性，不与首厂争抢现场实施资源。

### 3.2 建议的安全场景

| 场景 | 平台支持方式 | 首期边界和依赖 |
| --- | --- | --- |
| 高处作业 | 作业任务配置装备要求；带的有效异常上报形成事件；关联同人帽子联系 | 优先场景；挂接、扣合、冲击含义由厂商确认。不能把扣合等同于正确锚固 |
| SOS 与单人异常 | 记录人员、位置、来源、响应人；未响应升级；保留联系失败记录 | 优先场景；静默或跌倒仅在硬件具备并经测试后启用 |
| 外包检修 | 人员队伍、有效期、任务、领还、责任人和事件关联 | 先做基础资料和有效期；培训资质后台按客户流程后续细化 |
| 危险区域进入 | 区域权限、定位质量、进入停留判断、有效作业关联 | 试点选一个明确区域；定位漂移不直接判成违章 |
| 设备失去监护能力 | 断连、低电、状态过期、传感器故障，提示值班员核查 | 作为“监护信息不足”事件；不能推断人员已经安全离场 |
| 有限空间 | 作业清单、监护人、气体检测证据、通信、进入离开记录 | 第二阶段；气体设备、现场流程与适用制度明确后进入现场使用 |
| 应急撤离与点名 | 冻结事件时的人员快照，列出已确认、未确认、位置未知者 | 第二阶段；不能把设备离线当作人员已撤离 |
| 热环境作业 | 外部环境和作业时长提示、人工核查 | 后续探索；不从普通体温或心率直接诊断热射病 |

选择外包管理、责任落实和处置追溯作为扩展方向，与国家能源局南方监管局 2026 年 7 月关于现场作业、外包队伍及重大隐患治理的工作重点一致。这是产品方向参考，不代表本平台取得了合规认证。[国家能源局南方监管局相关通报](https://nfj.nea.gov.cn/xwzx/jgdt/202607/t20260702_304020.html)

有限空间模块应把监护人和现场检查证据作为对象。应急管理部的工贸有限空间规定解读强调监护、联络、检测和异常撤离；其适用行业边界不能自动套用于全部电厂，项目应由业主安全部门确认本厂适用规程，再配置验收清单。[应急管理部相关解读](https://www.mem.gov.cn/gk/zcjd/202312/t20231212_471584.shtml)

### 3.3 发散方向与投入次序

平台中长期差异化应来自设备数据对现场工作的实际帮助，而不只是增加穿戴品类。

1. **班前装备准备**：根据当天任务提示缺少的装备、即将耗尽的电量、待检设备；人工确认领取。可以先做检查清单，数据成熟后再做实时校验。
2. **检修期间临时队伍管理**：人员有效期、临时厂站授权、到期归还和资产缺失提醒，解决集中检修后的设备追收问题。
3. **交接班待办**：把未关闭事件、失联人员和待核实设备明确交给下一班，记录接交双方，不只是保留一个红色数量。
4. **设备健康和服务运营**：电池异常、反复掉线、传感器故障、送修和校准历史，为设备售后形成真实依据。
5. **事件复盘包**：按事件集中导出时间线、人员佩戴关系、位置质量、通信结果、图片和处置记录，减少人工拼接材料。
6. **工况模板**：高处、有限空间、单人巡查等任务模板；允许不同厂站选择装备要求和升级规则，避免每个客户改代码。
7. **重复异常分析**：先做规则和分组报表，区分设备故障、定位漂移、重复上报和实际风险，不直接把告警次数排名当成人员违章排名。
8. **AI 辅助复盘**：在数据质量稳定后提供摘要、检索和草稿，附来源。处置认领、关闭、广播和作业许可仍走确定性业务权限与人工操作。

第 1、3 项可以在一期以轻量方式加入；第 2、4、5、6 项在首厂稳定后滚动交付；第 7、8 项以真实数据积累为前提。开发过程中使用 AI，不意味着必须在首版产品中加入 AI 助手。

## 4 目标领域模型

### 4.1 基础对象

| 对象 | 最小设计 | 关键约束 |
| --- | --- | --- |
| Site 和 Space | 厂站、区域、设施、可选楼层和高程、坐标系 | 组织树、空间树、设备分组分别建模 |
| Person | 人员 ID、工号或外部标识、单位、班组、承包商、有效期 | 与 Account 分开；设备不再直接等同于登录用户 |
| ProductModel | 类型、厂商、型号、协议版本、能力定义 | 型号能力不是整个品类的固定能力 |
| Device | 平台 ID、外部 SN、型号、所属厂站、资产状态、网关关系 | 外部标识在约定厂商范围内唯一；设备 ID 长期稳定 |
| DeviceAssignment | 设备、人员、起止时间、办理人、归还原因 | 不覆盖旧关系；区间不重叠；同类数量限制按策略配置 |
| DeviceState | 最近可信遥测、发生时间、接收时间、质量、过期时间 | 资产状态、连接状态、穿戴状态分开 |
| LocationObservation | 来源设备、人员关联、区域、坐标、高度、精度、时间、来源种类 | 无可靠楼层时为空；保留实测、推断、人工登记差异 |
| WorkTask | 作业类型、厂站区域、时间、成员、负责人、监护人、外部票号 | 一人可参与多任务，事件匹配不唯一时标记待确认 |
| SafetyEvent | 来源、类型、等级、发生和接收时间、人员/作业/位置快照、规则版本 | 事件证据不被当前设备换绑覆盖 |
| EventAction | 认领、转交、处置、复核、关闭、重开、时间和操作人 | 追加历史，版本控制；不允许静默覆盖 |
| DeviceCommand 和 CallSession | 操作 ID、目标、请求人、幂等键、发送/回执/结束状态 | 第三方受理和设备执行分开；无回执则明确未知 |
| AuditLog 和 Evidence | 审计动作、对象、业务前后变化、证据存储键 | 权限和保留策略明确，导出下载可审计 |

实现顺序按业务闭环分批建表，不要求第一周一次完成全部模型。对可查询和有约束的核心字段使用明确列；厂商原始报文及低频差异字段可用受 Schema 约束的 JSON。不要把所有字段塞进一个通用 JSON，也不要一开始建设通用低代码物模型平台。

### 4.2 不能混用的状态

- 资产状态：在库、已领用、维修、停用、报废。
- 连接状态：在线、离线、未知，附最后确认时间和过期规则。
- 数据质量：有效、过期、传感器异常、时间不可信、缺失。
- 穿戴状态：按已确认协议定义，例如扣合、挂接、未确认；没有数据不设为正常。
- 人员状态：在场、离场、待核实；必须有可信来源，不能直接由设备在线推算。
- 任务状态：准备、进行、暂停、结束；只表达本平台监护上下文，不冒充工作许可。

### 4.3 事件与时间的一致性

统一报文至少包含 `eventId`、`deviceId`、`gatewayId`、`eventType`、`occurredAt`、`receivedAt`、`schemaVersion`、`payload`、`quality` 和厂商来源标识。厂站和人员关联由服务端可信资料确定，不能直接信任设备自报的权限范围。

业务幂等优先使用厂商消息 ID 和设备 ID；无消息 ID 时根据协议定义组合键和有限窗口，并保存原始记录。设备时间不可信时要保留接收时间及异常标记，不悄悄替换成可信发生时间。迟到消息按发生时的佩戴区间关联；历史绑定无法证实时保留人员未知，不用当前绑定人补齐。

同一异常的重复报文可以合并到一个待处置事项，但保留原始证据和重复次数。SOS 不受普通告警的静默规则影响。多设备关联先采取确定性规则，不引入不可解释的自动评分。

### 4.4 告警和通信状态机

事件主流程：新建 → 已认领 → 处置中 → 待复核 → 已关闭。低风险事件可以按明确策略简化复核；高风险事件要求有权限的复核人。误报是关闭原因，需要证据；不是直接删除事件。

认领使用版本号或条件更新；通知超时升级、交接班和重新打开均保留动作历史。通信失败不能自动关闭安全事件，传感器恢复也不自动等于现场问题处理完毕。

设备操作流程：待发送 → 已发送 → 平台受理 → 设备确认成功或失败；也可能超时、取消或结果未知。批量广播记录每台设备结果，不能用“总请求成功”替代“所有人听到”。是否能取得设备回执必须与供应商确认。

### 4.5 位置和分层厂区

先做稳定的二维视图及区域列表，再做可选 SVG 剖面，二者共用人员和事件数据。每个人显示一个当前可信位置，同时允许查看备选来源。位置选择综合来源能力、更新时间和质量，不能固定认为 GPS 永远优先。

高度值不直接等于楼层。没有室内定位、可靠高度校准或可信区域上报时，仅显示“楼层未知”。人工选择任务所在楼层要注明“任务登记位置”，不能绘制成实时定位结果。安全带借用同人帽子位置时显示“关联安全帽位置”和时间。

围栏先实现厂站区域、二维多边形、进入/离开、时间窗口、人员范围及防抖；有可靠楼层源后再启用立体区域规则。保存规则版本及生效时间，以便复盘。全厂精细 BIM、写实 3D、所有厂型模板不进入首期关键路径。

## 5 技术实施路线

### 5.1 模块化单体

继续使用一个后端部署单元，内部划分身份权限、人员资产、接入适配、状态位置、安全事件、通信、作业监护、报表运维。接口和表边界清晰即可，先不拆多个服务。

建议新增业务接口前缀 `/api/v1`，旧 `/hat/**` 通过兼容层逐步转接。PC 与 App 使用同一份接口契约，统一分页、错误码、时间格式、ID 类型、版本字段及“结果未知”的表达。先生成 OpenAPI 或等价可校验契约，再同步客户端，不让两人各自猜字段。

原始事件可靠入库后，再通过持久化待处理表或 Outbox 完成状态更新和消息通知；失败可重试、可核查。第一阶段不必引入 Kafka 或独立时序数据库。只有吞吐、保留量或高可用需求证明现有方案不足时，再增加基础设施。

已有技术版本较旧，启动阶段确定统一 JDK、Maven、Node 和 Flutter 工具链，并核实部署平台支持与依赖公告。工具链更新分独立变更回归，不能把所有升级与领域迁移混在一个大提交。具体版本以实施时官方支持范围和实际构建结果为准。

### 5.2 两端产品入口

PC 主导航建议为：值班台、人员与装备、作业监护、安全事件、位置追溯、调度通信、设备运维、平台设置。早期仅开放已完成模块；人员、设备和资产历史可先在同一分组内呈现。

值班台优先显示待处理事件、重点人员、位置可信度和责任人。视频按需打开，首期不默认全员拉流；视频成本、权限和网络负载均可控。对比深浅主题、屏幕字号和长时间值班可读性，在现场评审后定稿，不把 DOCX 的色值当成不可修改要求。

App 先做本组人员与装备查询、接收告警、认领处置、单人联系和我的待办。大型设备维护和规则编辑留在 PC。断网可保存草稿，但应急指令不得排队后在恢复网络时自动重放；提交结果不明先查询服务端。需要后台或锁屏可靠接警时，必须单独验证系统通知、权限和省电策略，不能靠一个前台列表证明。

### 5.3 接入和生产隔离

帽子通过现有厂商平台；带按实际协议选择 HTTP、MQTT、BLE 网关等路径，不提前假定。平台维护源设备与传输网关的独立身份。适配器负责报文认证、字段/单位转换、时间校验和异常隔离，业务层不依赖帽号。

演示模式需要独立数据、账号和部署配置；生产构建或启动检查禁止加载演示控制器、模拟种子和外部样例视频。页面显式显示来源，导出也带来源标记。当前演示兼容 Controller 未见配置条件隔离，应列入整改。

### 5.4 权限和运行安全

所有查询、详情、写入、导出、通信目标和 WebSocket 推送均检查操作权限与厂站/人员/设备范围。角色至少区分平台管理员、设备管理员、值班员、安全复核员、班组长和只读查看。平台管理员身份不能默认替代日常值班认领职责。

设备回调用供应商支持的签名或证书认证，并补时间窗口、防重放和幂等。供应商无法提供可信认证时，必须通过受控接入边界和设备身份核验设计解决，不直接开放匿名接口。下载只接受可信存储对象键或严格受控地址；登录响应不返回密码字段；日志不记录令牌、密码和完整敏感报文。

按照客户网络分区确定部署位置、允许的外连和 RTC/地图可用性。首期不向 DCS/SIS 下发控制命令。外网不可达时，提前验证地图底图、字体、视频 SDK 和通信依赖的降级方式；不能把“后端可启动”理解为离线环境所有功能可用。

## 6 两人和 AI 的协作方式

### 6.1 责任划分

| 工作 | A 主责 | B 主责 | AI 的作用 |
| --- | --- | --- | --- |
| 产品和现场流程 | 需求、原型、验收脚本、客户反馈 | 协助核实数据和接口可实现性 | 整理流程、生成场景和遗漏检查 |
| PC 和 App | 页面、状态管理、交互、端侧集成 | 审查权限契约和异常表达 | 页面实现、客户端适配、测试草案 |
| 后端和数据 | 用业务案例验收 | 模型、接口、事务、权限、迁移 | 生成实现、边界测试、代码检索 |
| 硬件接入 | 协调样机和现场人员 | 协议适配、日志、重放工具、通信联调 | 整理报文、编写模拟器和分析脚本 |
| 发布和质量 | 场景回归、验收记录 | 构建、部署、监控、恢复 | 自动检查、回归执行、发布材料 |

A、B 是责任位，可按两人的实际长处分配。每个高风险改动由另一人检查；无法检查事务或权限正确性时，先补知识或引入有边界的外部审查，不以 AI 自评代替验收。

### 6.2 容量约束

两人每周名义 10 人日，规划只排 6—7 人日的确定性开发，约 3—4 人日留给需求核对、联调、回归、客户沟通和故障。AI 提升的是产出速度，不预设固定“十倍效率”。前两周记录真实完成量，再修订后续估算。

并行最多推进两项需要人工验收的功能；涉及同一数据库或核心契约时先定契约再分工。PC 和 App 的大改不同时压在 A 身上：前半程以 PC 为主，后半程在服务端稳定后补 App。

### 6.3 每个 AI 任务的输入和完成条件

任务应明确业务目标、改动目录、接口和数据约束、禁止变动的部分、验收场景。把“大平台重构”拆成半天到两天可审查的小任务，例如“领用成功与审计必须同事务，失败全部回滚”，而不是让 AI 一次改完后端和所有页面。

每项工作至少产出代码差异、必要迁移、关键反向测试及运行证据。先由一人检查实现，再由另一人按业务场景验证；AI 可辅助找问题。避免让同一实现同时生成只验证自身假设的测试。

建议日节奏：开始时核对接口和阻塞；日间各自推进一个任务；结束前完成一次联调。每周保留半天跑主流程和更新风险清单，每两周交付一个可安装增量。冻结事件契约、状态机和权限约定后，变更需记录兼容影响。

## 7 分阶段开发安排

### 阶段 0 第 1—2 周 基线和协议准备

A：确定首厂、角色和前三个场景，整理真实演示流程，完成简版值班台与人员设备信息架构。B：确认仓库与历史文档差异，建立可重复构建、隔离测试库、版本化迁移和配置模板；修复关键入口及敏感字段问题的最小闭环。

两人共同：找回文档所述台账项目并做差异审查；拿到安全帽和安全带协议、样机、回执说明；冻结 Device、Person、Assignment、Event 的第一版契约。找回代码不盲目合并，以当前工具链重新验收。

退出条件：新环境可构建启动；已知高风险入口有整改方案及首批回归；厂商接口、待确认能力和负责联系人明确；首期范围形成清单。

### 阶段 1 第 3—6 周 通用台账和事件骨架

A：PC 登录厂站上下文、人员设备台账、领还详情和事件列表。B：厂站权限、人员型号设备、领用区间、资产状态、版本锁、审计事务，以及统一事件入库和状态机。

先用真实 HTTP 与数据库验证台账；设备事件使用专用模拟器，界面标记模拟。旧帽子接口保持可回归。此阶段可形成评审版，同时确认客户是否认可新业务对象。

退出条件：一人帽带并用、同设备并发领用拒绝、越权失败、审计失败回滚、重启后历史一致；模拟事件能认领和处置，不伪装成真实设备接入。

### 阶段 2 第 7—10 周 安全帽接入和通信闭环

A：值班台实时刷新、事件详情、位置来源、单人通信及未知状态。B：帽子适配、可信状态、回调认证、事件幂等、授权 WebSocket、SOS 认领与 RTC、操作记录和超时核查。

保留原始报文并建设可重放样本；通过厂商测试环境验证“请求受理”和“设备执行”的不同结果。先实现单呼和关键 TTS，复杂组呼与录制可在生产候选阶段补齐。

退出条件：真实帽子触发事件、授权值班员接警、真实接通后显示成功、失败可查；断开连接后恢复、服务重启和重复消息不破坏状态。

### 阶段 3 第 11—14 周 安全带和最小作业监护

A：多设备人员详情、任务成员与区域、装备要求、带事件关联帽子联系。B：带适配器、网关/子设备状态、规则有效期、发生时佩戴关联、事件历史快照。

现场只启用规格确认且已验证的安全带能力。先上线一个高处作业场景及一个 SOS 场景，避免把所有风险规则一起启用。区域和楼层数据缺失时诚实显示，不阻塞通用事件处置。

退出条件：同一人帽带真实链路走通；掉线、换绑、迟到消息、扣合与挂接区别、没有定位的带均有正确结果。

### 阶段 4 第 15—18 周 试点反馈和 App 核心流程

A：App 接警、查询、处置、单人通信，后台与锁屏提示验证。B：试点故障修复、数据量控制、通知补偿、备份恢复和运维告警；共同完成两轮现场反馈。

按首厂需要补二维围栏或轻量分层图，二者不同时扩成大型项目。没有可靠定位源时把分层图保留为区域示意。复杂组呼、交接班待办和证据导出按试点反馈排序。

退出条件：PC/App 同一事件状态一致；弱网草稿和结果核验有效；值班主渠道不依赖未经验证的 App 后台常驻。

### 阶段 5 第 19—24 周 生产候选和交付

完成角色矩阵、容量与稳定性测试、数据库迁移演练、备份恢复、发布回滚、最小监控、账号交付、现场培训和连续运行观察。整改期保留缓冲，不再插入新硬件类型。

退出条件：首厂验收场景通过，阻断级缺陷关闭；证据可追溯；恢复演练通过；数据来源和已知限制写入交付说明。没有通过真实设备和现场验收的模块继续关闭，不以总菜单数量补齐版本。

### 关键依赖和减范围顺序

关键路径是：基线与权限 → 通用身份和佩戴关系 → 可信设备接入 → 统一事件 → 真实通信和处置 → 现场验证。

厂商协议和网络条件在第 2 周仍不明确时，立即调整里程碑并继续台账和模拟契约工作。计划延期时依次推迟：新厂型模板、复杂分层视图、分析报表、批量通信高级功能、非试点设备类型。权限、事件真实性、并发一致性、回执结果和恢复验证不能删减。

## 9 验收标准和测试计划

### 9.1 必过业务场景

| 编号 | 测试场景 | 通过条件 |
| --- | --- | --- |
| A01 | 一人同时领帽和带 | 两条关系有效；设备数量为 2，人员数量为 1 |
| A02 | 两人同时领取同一设备 | 仅一人成功；设备、关系、审计一致 |
| A03 | 同人同类型上限竞争 | 若配置上限则数据库事务内生效，不能靠页面拦截 |
| A04 | 换绑后迟到告警 | 归属事发时人员；缺历史则待核实，不归给新使用者 |
| A05 | 未分配、维修或报废设备领用 | 按策略拒绝并返回明确原因 |
| A06 | 跨厂查询、详情、导出、通信与推送 | 未授权数据不可获取；不仅页面不可见 |
| A07 | 撤销角色/厂站权限 | 后续 HTTP 和实时消息立即按约定时限收窄 |
| A08 | 重复/乱序/重放/签名错误报文 | 重复不产生重复业务效果；不可信消息拒绝或隔离 |
| A09 | 两人同时认领事件 | 仅一个认领成功，另一端收到状态冲突 |
| A10 | SOS 接听与第三方故障 | RTC 真正加入后才显示接通；失败事件仍待处理 |
| A11 | 广播部分成功或无回执 | 单设备结果可查；无回执不能显示全部执行成功 |
| A12 | 子设备掉线而网关在线 | 子设备显示离线/未知，规则不按正常处理 |
| A13 | 定位漂移或楼层缺失 | 显示质量和未知；不会强行落到某层或自动判违章 |
| A14 | 数据库审计写入失败 | 领还或状态更新一并回滚 |
| A15 | 服务重启、断网恢复、消息补偿 | 已提交记录不丢；持久化待办恢复；操作不重复执行 |
| A16 | App 后台/锁屏/令牌过期 | 按目标机实测接警能力，过期后清理敏感状态和通信资源 |
| A17 | 历史设备调拨或人员离职 | 原事件归属保留；历史访问按归属和权限策略执行 |
| A18 | 演示环境和生产环境 | 生产无模拟资产/控制器/样例流，来源标记不可伪造 |

### 9.2 建议量化目标

启动时先约定试点规模，例如 100 人、200 台设备、10 个并发操作账号、同时 4 路视频。这是容量测试样本，不是已知客户规模。按设备每 10 秒一次状态上报估算，200 台约 20 条/秒、每日约 173 万条；需按报文大小和保留策略测存储，不能只以设备数量估算数据库。

建议在约定试点网络和测试数据量下，普通列表 P95 小于 1 秒，事件从平台接收至 PC 可见 P95 小于 2 秒；端到端时延另计传感器检测、硬件上报、网关及第三方平台耗时。对告警风暴和网络中断单独记录消息是否丢失和恢复耗时，不只看平均延迟。

备份恢复可先设试点候选目标 RPO 不超过 15 分钟、RTO 不超过 2 小时，必须通过相应备份/增量日志方案和恢复演练证实。紧急现场响应始终保留业主既有渠道；平台恢复目标不能理解为允许应急处置等待两小时。

上线前建议完成至少 7 天现场连续运行观察及多个班次交接，记录误报、漏报线索、未知状态比例、接警时间、掉线和通知失败。检测准确率与阈值由样机实测和业主验收确定，不在计划中编造。

### 9.3 每次发布的最小材料

版本号与提交号、安装包、依赖和配置说明、版本化数据库迁移、适配器版本、启用能力清单、测试记录、备份恢复记录、回滚步骤、已知问题、值班操作说明。测试区分模拟、真实 API、真实设备和现场四类证据。

## 10 数据迁移和旧系统退出

1. 冻结旧库只读快照并统计帽子、人员、绑定、事件和文件；核实当前数据真实性和归属，试导入在隔离库进行。
2. 建立 `legacy_device_mapping` 等映射，保存旧帽 ID、帽号和新 Device ID，明确新旧接口各自的数据权威。
3. 先迁移基础资产和当前绑定。旧库没有完整绑定历史时，标注“迁移前历史未知”，不能逆推出从未记录过的佩戴区间。
4. 事件和媒体按可证明来源迁移；关联冲突进入待核对清单。校验数量、关键字段、时间和映射，不只比较总条数。
5. 按厂站或账号灰度切换，避免两个系统同时修改同一资产；旧接口由兼容层转接，写入权威仅一处。
6. 演练回滚时考虑新系统已经发生的领还和处置，采用写入冻结、对账与恢复步骤；不能只回退程序却丢弃新业务记录。
7. 确认 PC、App、厂商回调和客户集成不再依赖旧接口后，再归档旧入口。旧事件保留只读查询和审计。

## 11 主要风险与对策

| 风险 | 早期信号 | 对策 |
| --- | --- | --- |
| 误把文档成果当成本仓库成果 | 找不到台账源码、迁移和测试 | 第 1 周找回并复核；未找到按新增开发排期 |
| 安全带能力不符合设计 | 只有扣合无挂接，或没有可靠上报时间 | 能力清单签认，按实测调整场景，不用 UI 补硬件 |
| 项目变成三端重写 | 两人长期只做页面，接口仍不稳定 | PC 优先，固定契约，App 后置，按闭环验收 |
| 第三方平台受限 | 网络不可达、无回执、RTC 无私有化条件 | 前两周验证现场网络；明确未知结果和替代联络渠道 |
| 地图看起来准确但数据不可靠 | 漂移、丢层、关联位置无标记 | 来源、精度、时间、未知状态进入模型和页面 |
| AI 生成代码推进过快 | 巨大提交、重复模型、测试仅覆盖成功 | 小任务、另一人复核、反向测试和真实报文回放 |
| 数据增长超出预期 | 高频遥测全量长期存储 | 按采样量估算，冷热保留、索引、归档，先压测再扩设施 |
| 首厂需求持续加码 | 同时要求两票、巡检、门禁、气体和 3D | 使用阶段清单，新增范围替换现有容量或明确后移 |

## 12 启动时需要确认的事项

不影响现在制定计划，但会影响范围和排期：两人的技术分工与每周投入；第一座落地电厂及主要场景；安全带型号、协议、样机和联网方式；厂内网络与部署系统；现有人员、工作票和定位系统；设备/人员/视频规模；资料保留要求；历史台账代码是否能找回。

在这些信息明确前，默认采用单客户私有化、首个厂站试点、安全帽与安全带两类设备、PC 优先、轻量任务关联、不做完整两票、不依赖实时楼层定位的方案。该默认方案保留多厂站权限基础，但不提前建设 SaaS 计费和复杂租户运营。

首个两周应交出四样具体成果：可重复运行的基线、确认过的设备能力清单、通用数据与接口契约、能被两人逐项验收的首版任务清单。之后每个阶段都围绕真实人员、真实装备和可追溯事件增加能力。
