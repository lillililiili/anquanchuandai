# 智能穿戴设备平台：原 PC 项目改造为后台管理系统整体方案

版本：V1.0 ｜ 编制日期：2026-09-16 ｜ 状态：供业务评审、技术设计与实施拆解使用

## 1. 方案结论与适用范围

在现有 Vue 3 PC 工程上改造后台管理系统，新建独立 PC 前台工程；安卓、前台、后台共用现有 Spring Boot 后端及统一业务数据。后端按管理、监护、设备接入分模块和接口边界演进，现阶段不另建一套重复后端。

后台负责设备资产和领用生命周期、人员账号、角色数据权限、组织与厂站、协助分组、接口集成和操作审计。实时监看、作业监护、调度通信、定位轨迹、告警核验和现场资料的主要操作入口迁入新前台。原有有效功能逐项确定去向、复用代码和验收项，完成替代验收后再切换旧入口。

统一产品名称采用用户指定的“智能穿戴设备平台”。后台名称建议为“智能穿戴设备平台 · 管理中心”，前台为“智能穿戴设备平台 · 监护前台”。PDF 中 ROLLING 标志的构图和位置保留为视觉基准，“融领管理中心”等文字作为品牌展示配置；正式产品名称不继续沿用“分体式智能安全帽平台”。

本方案依据后台 PDF 的全部 12 页、前台 PDF 的全部 17 页和当前工作区源码。页码是 PDF 文件物理页序，不是菜单顺序。仅进行了源码与设计静态分析，未进行真实硬件、生产数据库或外部系统联调；“有代码可复用”不代表相关设备链路已经验证。

### 4.1 视觉基准

## 5. 核心业务设计

### 5.1 设备主档、能力与状态

建立统一 `device` 主档，设备类型为 `HELMET`、`BELT`、`WATCH`。设备编号、厂商 SN、设备主键、厂商通道 UID 分开存储；人员主键不能使用安全帽编号代替。内部设备编号平台内唯一，外部身份按适配器/厂商及 SN 组合唯一，避免不同厂商序列号碰撞。

三类设备共享厂站、型号、供应商、采购批次、入库日期、资产编号、生命周期、当前领用、最后上报和协议版本；专属字段由设备扩展信息与能力表承载。安全帽保留视频/音频/拍照/定位适配；安全带挂接、受力等按协议确认；手表的通信、提醒、位置、传感能力分别登记，不默认有心率、血氧、跌倒检测等功能。

必须独立保存和展示以下维度：

| 维度 | 建议值/数据 | 用途 |
| --- | --- | --- |
| 生命周期 | 库存、使用中、维修中、停用、报废 | 是否可领用、送修、报废 |
| 通信状态 | 在线、连接中断、离线、未接入、未知 | 结合来源、最后心跳、协议阈值判定 |
| 数据新鲜度 | 最新时间、已过期、无数据、异常数据 | 电量/位置/传感数值是否可当作当前值 |
| 能力状态 | 未确认、待联调、已验证支持、不支持 | 是否提供视频、语音、定位或传感动作 |
| 现场核验 | 未核验、核验进行中、已有核验记录等 | 反映人工核验，不从“在线”推断安全结论 |

安全带通过安全帽/网关转发数据时，保存 `gatewayDeviceId`、通信链路及源时间；分别呈现“安全带到网关”与“网关到平台”的诊断信息。网关离线造成的下游失联需关联原因，避免被解释为多个独立穿戴违规事件。

### 5.2 领用、归还与当前绑定

领用是形成当前人员绑定的正式入口，设备建档不等于领用。一个人员可同时领用帽、带、表；建议默认每种类型一件，另加设备按业务规则放开，不能强制每个人必须三件齐全。PDF 中“添加其他装备”对应可扩展领用明细。

办理时由后端校验人员有效、人员和设备在操作者授权范围、设备属于当前厂站、设备为可用库存、无现存领用；提交采用幂等请求号、事务和条件更新/唯一约束，两个管理员同时领同一件只允许一笔成功。所选多件设备默认整单成功或整单失败，失败列明冲突设备，防止界面显示整套领用而实际只成功部分。

领用记录保存领用人、部门/班组快照、设备明细、经办人、实际发生时间、系统登记时间、用途、备注和版本。系统经办人取登录身份，不能由前端任意传入。补登记需专门权限并说明，不允许伪造当前操作时间。

归还支持按设备部分归还；每件设备分别关闭有效领用区间，未归还的其他装备继续显示使用中。正常归还转库存，损坏归还先记录验收，再进入送修。需要更正历史时增加更正记录，不直接覆盖旧经办人、时间与绑定对象。

新增绑定、归还、当前设备关系、生命周期与审计在一个本地事务提交；成功后推送变更，前台人员装备列表更新。跨服务通知或厂商接口不应被放进持锁事务，使用提交后事件与重试机制。

### 5.3 生命周期和运维

| 当前状态 | 动作 | 前置条件 | 结果与保留内容 |
| --- | --- | --- | --- |
| 库存 | 领用 | 有效人员、范围匹配、设备可用且未领用 | 使用中；生成领用记录 |
| 使用中 | 归还 | 有效领用记录、归还验收 | 库存；关闭相应明细，保留历史 |
| 库存 | 送修 | 维修原因、处理人 | 维修中；创建维修单 |
| 维修中 | 维修完成 | 结果和检测记录、验收通过 | 库存；维修记录归档 |
| 库存/维修中 | 停用 | 有原因；维修中须同步关闭或挂起维修单 | 停用；不可领用 |
| 停用 | 恢复库存 | 检查通过、恢复原因、无活动维修单 | 库存；记录恢复动作 |
| 库存/停用/维修中 | 报废 | 无活动领用；维修单已处理；原因、编号复输、确认 | 报废；禁止恢复使用，历史可查 |
| 使用中 | 送修/停用/报废 | 先办理归还；禁止直接跳转 | 返回明确业务错误，导向归还流程 |

PDF B09 顶部箭头表示生命周期概览，实际采用上述有条件的状态转换，不要求每件设备必须维修后才可报废。业务报废不等于物理删除档案。误报废通过专项数据更正流程处理，不提供普通“恢复使用”按钮。

### 5.4 组织、厂站、人员与账号

复用 `sys_dept` 表示集团、公司、部门、班组的组织关系；新增厂站及区域空间树。组织可以关联多个厂站，厂站含多个区域；树的关联只表达业务关系，不自动授予账号跨厂站访问权限。

为“人”与“登录账号”建立明确关系。建议人员档案独立于登录账号：现场人员即使没有 App 登录账号也可以领用设备；有账号时关联现有 `sys_user`，保留旧用户主键映射。禁用账号应阻止登录及撤销会话，但不能自动归还该人的装备或抹除历史。

人员外部系统同步时使用外部人员编码映射，重名不自动合并。厂站和区域编码作为稳定标识，名称可修改；修改名称后历史事件仍显示发生时快照。存在活动设备、作业或子节点的组织/区域停用前提示影响，历史查询保留。

“当班人员”需要班次或在岗名册，不等于系统用户列表，也不等于在线设备数。建议一期支持本厂站当班名册维护/导入，并可对接外部排班；名册维护放入用户管理的二级标签，监护前台消费同一数据。

### 5.5 协助分组

以人员成员为基础，终端是成员当前可达的 PC、APP 或安全帽通信端。角色（系统功能权限）、组织班组（人员归属）、协助组（通信协作）、作业成员（任务责任）分别建模。

分组保存厂站、负责人、名称、描述、启停状态、人员成员和 SOS 通知范围。成员终端随登录或领用变化解析；会话开始时保存参与者与终端快照，归还旧安全帽后不能继续被当作原人员接收新的定向通知。

PDF B08 的终端行可以显示为“成员+终端”的展开视图；同一个人的 PC 与 APP 都在线时避免重复计算人数。新增成员需检查操作权限和目标厂站；协助组成员资格不隐式赋予组内所有设备的查看权。系统必须为受邀用户授予明确、限时、限对象的会话权限，或仅向已有相应授权者发送可操作邀请。

### 5.6 角色、应用权限和数据权限

保留若依角色、菜单、按钮权限体系，增加 `admin` 与 `portal` 应用可访问性及厂站/区域授权。建议模板包括系统管理员、厂站管理员、设备管理员、值守员、监护员、现场人员；工作负责人既可是一种功能授权，也应记录在具体作业中，不能仅靠全局角色判断谁负责某一任务。

授权判断是“该操作在该对象所属范围内是否被某一有效授权允许”。多角色应按同一角色的操作与范围组合后取并集，不能把角色 A 的全部功能与角色 B 的全部厂站做交叉组合，造成权限扩大。默认无授权即不可访问。

列表、详情、导出、附件、视频地址、设备命令、批量操作和 WebSocket 都校验相同数据范围。前台“当前厂站”是查询上下文，实际授权以服务端为准。部门权限不能替代独立的厂站/区域权限。

迁移时新用户按最小权限创建；老用户先核对业务角色和厂站再生成新授权。新旧接口均须加同等服务端授权，防止新接口限制后仍能通过旧 `/hat/**` 绕过。

### 5.7 接口集成和审计

接口集成至少覆盖 B04 六类连接器。现有安全帽 `HeadbandService` 作为第一个适配器，安全带与手表按厂商协议新增；工作票/人员/安监适配器分别处理业务映射、来源版本和回执。通信连通、鉴权成功、字段匹配、数据业务验证、上线启用是不同状态，不能只返回 HTTP 200 就显示“接入成功”。

配置按环境隔离，敏感凭据后端安全存储、界面脱敏且不记录明文变更值；测试连接只能访问受控的配置目标。保存配置、测试连接和生产下发分为不同动作及权限。演示结果始终带演示标记，不能修改生产连接状态。

对外回传分事件摘要和核验记录两类，每类保存请求标识、负载版本、目标编号、回执时间、状态、次数和最后错误。摘要回传成功不等于核验记录提交成功，更不等于原安监系统正式结案。失败重试须幂等、限次和退避；业务拒绝应人工处理，不无限重试。

审计复用若依操作日志能力，同时补业务对象、厂站、来源客户端、结果、追踪号、变更前后快照和关联记录。关键状态变更与审计可靠落地；日志按权限查询，不向普通业务用户提供“清空全部”操作。用户密码、设备凭据、RTC Token 不进入快照；示例中“待联调”应与真正的执行失败区分。

## 6. 共用后端与数据改造

### 6.1 服务模块划分

建议先在现有多模块工程中按包分离 `identity`（身份权限）、`asset`（台账领用运维）、`site`（厂站区域）、`monitoring`（作业与核验）、`communication`（通信）、`integration`（接入回传）。接口层和核心业务层分开，后台与前台的 Controller 可以不同，但必须调用相同的领用、事件和权限服务。

目前 `ruoyi-admin` 是启动/接口模块名称，不代表它只能服务 PC 后台。可继续使用现有启动模块，逐步将新增领域放入独立业务模块，避免把拆分前端变成全面重写若依架构。

新接口建议使用 `/api/admin/v1/**`、`/api/portal/v1/**`、`/api/integration/v1/**`；安卓先保留 `/login`、`/getInfo`、`/hat/**`。旧 `/dev-api`、`/prod-api` 是网关或开发代理前缀，不是业务领域。不能一次性更改旧接口路径、分页格式和字段名而要求安卓立即同步发布。

### 6.2 建议逻辑数据模型

下表为逻辑设计，不是已执行的建表脚本。可按后端实体规范确定最终物理表名；优先关系表和必要索引，不把核心可查询字段全部塞入 JSON。

| 实体 | 关键字段/关系 | 主要规则 |
| --- | --- | --- |
| `device` | deviceId、deviceCode、type、vendorId、SN、model、siteId、lifecycle、version | 统一三类设备主档，稳定身份 |
| `device_external_identity` | deviceId、adapterId、externalId、旧 hatId/hatNumber | 外部与旧接口映射；迁移可追溯 |
| `device_capability` | deviceId/modelId、capabilityCode、支持/联调状态、验证版本/时间 | 能力与运行时状态分别维护 |
| `device_latest_status` | deviceId、communicationState、lastSeenAt、gatewayDeviceId、battery、sourceTime、quality | 最新状态只接纳更新的数据；历史上报另存 |
| `device_status_history` | deviceId、类型、源时间、接收时间、原始来源、数据质量 | 重建状态与诊断断连原因 |
| `person` | personId、personCode、sysUserId（可空）、externalPersonId、deptId | 人员与登录账号分离 |
| `site` / `site_area` | siteId、type、areaId、parentId、geometry、coordinateSystem、version | 厂站/区域与组织独立 |
| `org_site_relation` | deptId、siteId、关系类型 | 关系不等于授权 |
| `role_scope_grant` | roleId、permission/app范围、siteId、areaId | 功能及空间授权一起评估 |
| `duty_shift` / `duty_shift_member` | shiftId、siteId、起止、personId、来源 | 当班名册，不以设备在线推算 |
| `equipment_issue` / `equipment_issue_item` | issueId、personId、deviceId、领用/归还时间、用途、人员组织快照 | 明细支持部分归还，当前有效关系唯一 |
| `device_current_assignment` | deviceId（唯一）、personId、issueItemId、version | 当前绑定投影；由领用事务维护 |
| `maintenance_order` / `device_lifecycle_log` | deviceId、故障、处理人、状态、前后状态、发生/登记时间 | 维修和生命周期留痕 |
| `assistance_group` / `group_member` | siteId、负责人、personId、通知范围、有效时间 | 保留旧 groupId 映射，不把设备数量当成员数量 |
| `communication_endpoint` | personId、clientType、deviceId或sessionId、providerUid、可达状态 | 终端和业务人员之间的动态关联 |
| `integration_config` / `integration_job` / `integration_delivery` | 环境、连接器、配置版本、目标、幂等号、回执 | 同步与回传可重试和追踪 |
| `business_audit` | actor、app、object、siteId、动作、结果、traceId、脱敏前后快照 | 跨三端追溯 |

前台新增的 `work_context`、`event`、`verification_record`、`media_relation`、`communication_session` 等在配套方案定义，与本表引用同一 `personId/deviceId/siteId`。

厂站权限和事件追溯的核心索引至少覆盖设备厂站及状态、有效领用唯一性、人员领用时间、厂站事件时间、外部编号唯一性、回传幂等标识。数据库实际版本与存量约束检查后再确定索引实现，不能仅靠前端禁用按钮保证唯一性。

### 6.3 建议后台接口清单

以下路径是新接口设计建议，不声称当前已存在；均位于 `/api/admin/v1`。

| 接口组 | 示例接口/动作 | 关键行为 |
| --- | --- | --- |
| 台账 | `GET/POST /devices`；`GET/PATCH /devices/{id}` | 分页筛选、建档、按版本编辑；状态变更用专门命令 |
| 档案 | `GET /devices/{id}/capabilities`、`/history`、`/integration-status` | 分页历史、能力及数据来源 |
| 领用 | `GET /issuances`；`POST /issuances` | 请求幂等、批量明细事务 |
| 归还 | `POST /issuances/{id}/returns` | 按明细部分归还，验收结果 |
| 运维 | `POST /maintenance-orders`；`POST /maintenance-orders/{id}/complete` | 维修流程及结果 |
| 生命周期 | `POST /devices/{id}/disable`、`/restore`、`/scrap` | 校验合法转换、版本及原因 |
| 人员与账号 | `/persons`、`/users`、`/duty-shifts` | 人员/账号映射、名册；既有若依接口按需复用 |
| 组织空间 | `/departments`、`/sites`、`/areas`、`/org-site-relations` | 独立树和关联 |
| 授权 | `/roles`、`/roles/{id}/grants`、`/roles/{id}/users` | 菜单、操作和厂站区域同源 |
| 协助组 | `/assistance-groups`、`/{id}/members`、`/{id}/sos-policy` | 分组成员与终端能力分开 |
| 集成 | `/integrations`、`/{id}/test`、`/{id}/sync-preview`、`/{id}/sync`、`/deliveries/{id}/retry` | 预览后确认真实同步；错误与回执可查 |
| 审计 | `GET /audit-records`、`/{id}`、受控导出 | 不暴露普通删除接口 |

统一新接口响应中携带 `requestId`，列表采用一致的分页约定；旧接口保持原响应包裹，由兼容层转换。冲突和业务禁止返回清晰错误码，如 `DEVICE_ALREADY_ISSUED`、`DEVICE_STATE_CONFLICT`、`SCOPE_DENIED`，前端展示可理解的提示。

### 6.4 老安全帽与安卓兼容迁移

第一步盘点真实安全帽、人员、群组、历史事件和文件，区分真实数据、演示记录、无主记录和重复 SN。建立迁移批次和映射表，缺厂站或人员身份不清的进入待归属队列，不凭名称猜测。

第二步为安全帽建立 `deviceId`，保留原 `hatId/hatNumber` 与媒体、通道字段。旧记录未必具备完整领用历史，只能生成“迁移时点的当前绑定快照”，历史起始时间缺失则注明未知；不能编造几个月前的领用/归还记录。

第三步让所有新领用、归还及老绑定写接口进入同一服务。保留的旧帽子表可作为兼容投影/类型扩展表，但当前人员绑定只有一个权威写入口；本地关系更新需要事务和一致性校验，禁止两套代码独立双写。

第四步将旧报警、SOS、文件和轨迹映射到统一设备。历史人员关系以发生时的绑定区间解析；缺证据的记录保留旧快照并标注不确定，不用当前使用人覆盖历史所有者。旧报警与围栏报警归并时用来源+原始记录 ID 防重。

第五步对安卓 `/login`、`/getInfo`、设备列表、本人设备、轨迹、围栏、报警、对讲、TTS 做契约回归。安卓旧 `/hat/**` 默认仍表示安全帽，不直接返回安全带/手表混合集合。涉及新核验流程时，旧“处理完成”应记录为旧端处理动作，不能伪装成新核验提交或外部正式结案；需要核验的返回可解释的升级/补核验提示。

第六步按厂站灰度切换、校验记录数和状态后再停止旧 PC 入口写入。回退旧 UI 不回滚已经发生的真实领用和归还；应通过兼容层读取新权威状态，保持交易历史。所有数据库变更先备份、试迁移、核对，再进入正式迁移。

## 7. 两端部署、登录与实时通信

建议两个独立静态应用部署在同一受控域名的 `/admin/` 与 `/portal/`，后端 API 使用 `/api/`，保留安卓旧入口。独立静态构建不等于独立数据库；无需在本轮引入微服务或多套账号中心。

两端入口分别校验 `admin:access`、`portal:access`。若需要点击“管理中心/返回监护前台”免重复登录，建议由服务端提供短时、一次性、绑定目标应用的会话交换票据，兑换完成立即清理浏览器 URL；用户和会话从后端验证，不能在 URL 中传长期 Bearer Token。也可以后续统一为服务端 Web 会话，但需配套 CSRF 机制，不能仅修改 Cookie 存储方式。安卓保留自己的登录会话。

当前 [WebSocketSever](</E:/沉积岩/anquanchuandai/后端代码/melhat_server-dev/ruoyi-system/src/main/java/com/ruoyi/system/websocket/WebSocketSever.java>) 使用 `client + type` 保存连接，旧 `type` 区分 PC 与 APP；新前后台同时打开时必须引入应用和独立会话标识，不能互相覆盖。客户端路径中的 userId/type 不能作为身份依据，握手需校验会话或短时票据。

当前 [ExternalController](</E:/沉积岩/anquanchuandai/后端代码/melhat_server-dev/ruoyi-admin/src/main/java/com/ruoyi/web/controller/business/ExternalController.java>) 报警/SOS存在全量广播调用，定位保存后的推送被注释。改造应实现鉴权订阅、按厂站和对象推送、断线重连后补取最新快照。涉及 RTC 凭据的消息只发送给获授权的会话参与者，不能全量广播。

单后端实例可先用可靠数据库事件/Outbox加现有缓存做推送协调；如部署多实例，则必须增加跨实例事件分发、定时任务主执行者控制和去重。媒体流沿用已验证的厂商流服务/RTC链路，后端负责权限与短时访问地址，不默认由业务服务转发全部多路视频。

## 9. 验收标准

### 9.1 界面验收

- B01-B12 分别建立页面/状态截图记录，使用相同视口、固定测试数据逐页对照。核验顶栏、侧栏、筛选、表头、设备图片比例、抽屉、详情分栏、标签及按钮位置；差异修正以原图为准。
- B02 新增、B07 编辑、B09 报废确认、B06 授权树、B01 领用归还切换均有真实可操作表单；不能只做截图中静态状态。
- 三种设备档案保持 B10/B11/B12 各自布局，不能都压成一张通用表格。
- 无数据、加载失败、无权限、数据过期、接口未配置、设备能力未确认等状态不占用虚构数值；正文与抽屉可滚动且不遮挡提交按钮。
- PDF 中没有给出的后台登录页、维修单详情、归还表单等，用同一组件和浅色视觉补齐，并在设计评审中单列为补充页。

### 9.2 业务与兼容验收

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 新建安全带/手表 | 库存、未绑定；不自动显示在线或传感正常 |
| A02 | 两人同时领同一设备 | 仅一单成功，另一单明确冲突；无孤立明细 |
| A03 | 三件领用、只还安全带 | 帽表仍使用中，带进入库存；前台同步展示 |
| A04 | 使用中设备报废 | 服务端拒绝并提示先归还，调用旧API也不能绕过 |
| A05 | 归还后报废 | 原领用、维修、事件和媒体仍可追溯 |
| A06 | 安全带失联 | 只改变通信/新鲜度，不自动判定挂接违规 |
| A07 | 切厂站/伪造详情ID | 查询、导出、附件、视频、WS与命令均遵守授权 |
| A08 | 账号禁用/角色变更 | 会话和授权按策略失效，装备领用历史不被删除 |
| A09 | 修改协助组/换设备 | 新通知送到当前授权终端，历史参与者不被重写 |
| A10 | 外部接口超时并重试 | 一次业务结果，无重复设备/事件；保留每次尝试记录 |
| A11 | 原帽子同步 | 不覆盖本地领用、人员、厂站归属与已配置媒体信息 |
| A12 | 安卓兼容 | 原查询/对讲/广播契约有效；旧处理动作不伪装新核验 |
| A13 | 生产/演示隔离 | 演示数据不计入真实统计，不发真实命令，不误报回传成功 |
| A14 | 历史绑定迁移 | 无依据的时间保持未知；事件归属不随今天的绑定改变 |
| A15 | 前后台同时在线 | WS不会互相覆盖或跨厂站串消息 |
