# 智能穿戴设备平台：新 PC 监护前台整体搭建方案

版本：V1.0 ｜ 编制日期：2026-09-16 ｜ 状态：供业务评审、技术设计与实施拆解使用

## 1. 建设定位和推荐方案

新建独立 Vue 3 PC 前台，按领导提供的深蓝色界面逐页还原，承接原安全帽平台的监看、调度、地图、轨迹、围栏、报警、文件等可用能力，并围绕“人员—三类装备—作业—事件—现场核验—证据—外部回传”建立关联流程。

PC 前台、改造后的管理后台、安卓端共用现有 Spring Boot 业务后端；前台按页面需要新增聚合查询和业务接口，不复制整套后端和数据库。原 PC 工程继续用于管理后台，新前台独立构建、部署和发布。

产品统一名称采用用户指定的“智能穿戴设备平台”。前台建议展示“智能穿戴设备平台 · 监护前台”，保留 PDF 中 ROLLING 的视觉位置和品牌构图。PDF 原标题“融领智能穿戴安全监护平台”作为品牌文案参考，不延续旧“分体式智能安全帽平台”名称。

本方案已视觉检查前台 PDF 全部17页、后台 PDF 全部12页，并对照当前工作区源码。页码均为 PDF 的物理页序。代码可复用结论来自静态分析，不代表真实硬件、网络、生产数据库和外部接口已完成测试。

### 1.1 需求依据与边界

- **PDF明确**：深蓝监护界面、九个一级菜单、三类装备、工作票只读关联、事件现场核验、回传、SOS演练、数据缺口和能力未确认的表达。
- **代码现状**：已有安全帽列表、地图、围栏绘制、轨迹查询、FLV播放、Agora通话、TTS、报警、文件及统计等实现；需改造和联调后复用。
- **方案建议**：新增人员/设备/作业聚合模型、事件状态分层、接口契约、增量订阅、数据迁移、回归和验收规则。
- **待确认**：真实设备协议与能力、厂区底图、外部工作票/安监接口、品牌原素材、使用规模、业务参数。

PDF 中按钮及演示文案作为设计要求分析，不构成本次实际发送广播、变更权限或执行报废的授权。当前交付是方案，应用搭建属于后续实施。

## 2. 信息架构与前后台职责

前台一级菜单按原图顺序为：综合总览、人员与装备、作业监护、视频监看、调度通信、定位与轨迹、告警与核验、现场资料、统计追溯；“管理中心”固定在侧栏底部，仅对具有后台访问权限的用户显示。

| 业务 | 管理后台负责 | 监护前台负责 | 数据关系 |
| --- | --- | --- | --- |
| 人员与装备 | 人员/账号、设备档案、领用归还、生命周期 | 当前人员、三件装备、状态、历史只读查看 | 同一人员和领用关系 |
| 组织与范围 | 组织、厂站、区域、角色与范围授权 | 厂站切换、区域筛选、授权范围内监护 | 同一厂站/区域主数据 |
| 协助分组 | 分组成员、负责人、SOS通知范围 | 按组通信，授权用户可快捷建组 | 同一分组服务和审计 |
| 作业 | 外部系统连接、字段映射 | 关联已有作业、监护、参与人和事件展示 | 原工作票许可、审批、销票保持来源权威 |
| 设备异常 | 接入与阈值配置、维修处理 | 查看异常、认领、现场核验、关联证据 | 异常事件与运维单可关联，不混用状态 |
| 视频/对讲/TTS | 接入配置、能力确认、审计 | 多路视频、远程指导、单呼群呼、广播、SOS | 统一媒体访问和通信服务 |
| 定位/围栏 | 厂站底图及区域基础配置 | 定位、轨迹、围栏绘制与进出提醒 | 复用原空间能力，统一权限 |
| 现场资料/统计 | 数据保留、导出授权、审计 | 检索、预览、引用、受控下载、追溯 | 关联原始文件与事件，不复制成孤立资料 |

前台不是只读大屏，而是值守和现场协作的工作系统，允许认领、核验、通信、围栏编辑等业务操作；资产领用、报废和系统授权仍在后台完成。

## 4. UI 还原规范

### 4.1 视觉和页面结构

以 1672 × 941 原图尺寸建立首次对照视口，另验证 1920 × 1080、1440 × 900。保持深蓝底、蓝青边框、白色主文字、浅蓝次文字、亮蓝按钮、青绿在线、橙黄待核验、红色求助/危险动作。状态始终配文字和图标，不能只靠颜色。

顶栏、九项侧栏、底部管理中心位置统一；各页卡片、地图、侧面板、视频比例依照相应页面实现。F17 不增加原图没有的大型装饰标题或图表；F03/F11/F12 不简化为默认后台表单；F04/F08 保持媒体优先的布局。

建议组件封装为 `PortalLayout`、`Panel`、`MetricStrip`、`FilterBar`、`PersonEquipmentStatus`、`DeviceStatusBadge`、`DataFreshness`、`WorkSummary`、`EventSummary`、`VideoPlayer`、`MapViewport`、`TraceTimeline`、`VerificationForm`。这些是实现建议名称，不是已有组件。

色值、字体、间距、边框透明度、圆角和栏宽在逐页对照中取样并形成样式变量。原图页面间图标与菜单缩进略有差异，组件统一时保留菜单顺序和总体视觉，差异以代表页确认；不把偶然的生成图标误差作为业务差异。

地图应保持设计的俯视厂区视觉与图层组织。PDF 中的“厂区示意·非实测”不能直接当作已配准地图；若暂用示意图，必须明确模式，不把真实坐标随意投到图片上。真实部署要有校准底图、坐标系和区域边界。

照片、设备图、头像、Logo与登录背景尽量使用原设计素材；如只能取得PDF，提取或裁出独立图像作为视觉参考，并标明演示素材，不能截取整页充当功能界面。产品图比例保持原图，素材内容最终与实际交付硬件一致。

### 4.2 必须补齐的交互状态

PDF多为选中行、打开抽屉和示例异常状态；还应设计初次加载、空数据、筛选无结果、接口失败、无权限、连接恢复、数据过期、提交中、并发冲突、未保存离开等状态，延续原图风格。原图未给的广播/会话历史、进出围栏记录、作业关联弹窗等应列为补充界面。

所有新增内容优先放在既有二级标签、详情或抽屉中，不擅自增加一级菜单。实时更新不得抢走正在输入的核验表单焦点，也不得因列表排序变化自动切换正在监看的人员。

窄屏时允许局部表格横向滚动、右侧详情转抽屉，地图/视频随容器调整。不要将整个系统等比例缩成小字大屏；以PC常用窗口可读可操作为验收依据。

### 4.3 示例一致性处理

PDF中的同名人员对应帽子编号、电量、班组、时间在不同页面存在示例差异，实施时从同一测试数据集生成各页，不照抄为冲突业务数据。F04的“1+7”应按8个唯一设备分配槽位，主画面与底部选中缩略图即使重复展示，也不重复计算设备数。

“设计预览/示例画面/非实时”仅用于真实的演示状态。生产不展示虚构图表或回传成功；断流显示最后一帧时标出最后帧时间，不能继续叠加当前时钟制造实时效果。

## 6. 业务主链路设计

### 6.1 人员、三类装备与当班统计

采用后台统一的 `personId`、`deviceId`、`siteId` 与领用关系。前台按人员聚合其当前有效领用装备，三类装备不要求必须全部配齐；缺少装备显示“未领用”，不能显示“离线”，也不能为了凑满三列创建虚假设备。

一名人员可能没有工作账号，也可能同时有APP、PC与安全帽终端，人员数按 `personId` 去重。人员是否当班来自有效班次名册，不能从安全帽在线状态推断；作业参与人数从作业成员获取，重复参与多个作业时总览人员数仍去重。

设备的生命周期、通信状态、数据新鲜度、能力和现场核验分别展示。电量低不意味着离线；“使用中且连接中断”可以同时成立。通信在线仅说明可达，不能显示成“安全正常”。

F03/F07中的历史绑定按领用生效区间查询。人员A归还帽子后人员B领用，A昨天的轨迹、影像和报警仍属于当时关系，不能因今天绑定B而改写历史。

### 6.2 作业来源关联与监护

PDF要求原工作票系统负责许可、审批、销票；本系统只读同步来源摘要，并建立监护上下文。作业来源还包括巡检、检查任务，按 `sourceSystem + sourceType + externalId` 唯一映射为 `workId`，不要把当前接口文件中的旧审批动作恢复成新的一级业务。

“关联已有作业”流程建议：选择授权厂站 → 查询/选择来源任务 → 查看工作票、时间、区域、负责人、监护人和参与者 → 校验外部人员/区域映射 → 保存本地监护关联。来源字段只读；本地可补监护备注和经授权的协作信息，不覆盖原许可状态。

若暂无来源接口，一期可配置“手工登记外部编号”的过渡入口，标记“待来源核对/未同步”，不允许手工把许可状态改成“已许可”。该过渡是方案建议，不是PDF已确认功能；不默认自建审批引擎。

将状态分为：来源业务状态、来源同步状态、本地监护状态。工作票已经结束不自动代表事件已核验；同步失败显示上次成功时间，不能清空原快照或默认已取消。来源有版本号则按版本更新，否则用更新时间和幂等校验。

作业详情聚合参与人员、实际领用装备、在线状态、已验证的视频源、当前异常、地图区域、来源风险摘要与现场记录。PDF中的镜头1至4应对应真实可访问设备，不能假定每个作业有4路视频。人员与作业关联不能仅靠“同一时间在区域内”自动确认，应优先用来源成员映射和明确关联。

### 6.3 统一事件、现场核验和原安监回传

事件来源包括安全帽现有 SOS/静默/脱帽/跌落/近电等已定义类型，以及新增设备通信中断、低电量、位置待核验、围栏进出等。新传感类事件必须有协议或明确规则依据，不能把安全带连接中断转换成未挂接违规。

设备原始告警与平台衍生事件保留来源区分，按来源消息ID防重；同一设备持续断连在同一次异常期间更新一个事件，而不是每次心跳超时新增一条。连接恢复记录恢复时间和证据，不自动替代现场核验。

| 独立状态维度 | 建议状态/数据 | 说明 |
| --- | --- | --- |
| 异常信号 | 活跃、恢复、未知；开始/恢复时间 | 设备通信或传感事实 |
| 本地跟进阶段 | 待认领、处理中、待现场核验、已完成本地核验 | 通过明确动作和权限流转 |
| 核验记录状态 | 无记录、草稿、已提交；版本、提交人/时间 | 草稿不等于已核验，提交不代表外部结案 |
| 核验结论 | 设备通信异常、需现场处理、暂无法确认等 | F12给出示例；后两类可要求继续跟进 |
| 摘要回传 | 未发送、待回传、发送中、成功、失败 | 与核验回传分别保存 |
| 核验回传 | 未提交、待回传、发送中、成功、失败 | 只回传正式提交版本 |
| 原安监业务 | 外部事件编号、状态、同步时间 | 正式结案在原系统；本系统只读 |

建议事件处理顺序：接收/规则触发 → 去重并建立人员/设备/作业快照 → 值守员认领 → 远程查看或联系现场 → 保存核验草稿 → 提交现场情况和结论 → 后台排队回传 → 展示原系统回执和状态。

“待现场核验”可由事件类型规则直接要求，也可由处理者转入；实际负责人另存字段，不能只从标签判断是否已认领。认领采用版本检查，两个值守员同时认领只有一个成功，另一人可查看当前负责人并走有权限的转交。

核验表按F12实现必填结论、现场情况、后续措施、现场照片；照片支持 JPG/PNG、单张不超过10MB，与PDF保持一致。文件数量上限和总容量在详细设计确定。草稿可反复保存但不更新“已核验”指标；正式提交后保留版本，补充说明创建新版本和变更记录。

“暂无法确认”“需现场处理”可以提交核验记录，但本地待跟进状态继续保留，不能一律置为完成。F01“已核验”可按存在正式提交记录统计，同时提供“仍需跟进”数量，避免把完成记录与解决异常混成同一指标；具体统计定义写入第10节。

事件建立后保存发生时人员、厂站、区域、作业、设备关系、数据时间和规则版本。没匹配到作业时显示“未关联”，不按最近任务强行绑定。后续补关联需审计，不修改原设备消息。

摘要回传和核验回传使用不同幂等键和记录，保留请求版本、回执、外部编号。网络失败只改变回传状态，本地提交记录仍成功保存；业务拒绝提示具体原因，由有权人员更正后发新版本。

### 6.4 视频墙与单路监看

复用现有 FLV 播放逻辑与 Agora 接入封装，将“监看流”“互动通话”“录像”“抓拍”拆成独立能力与状态。设备通信在线不等于视频可用；SDK加入频道也不等于远端有人接听。

F04支持1+7、2×4、3×3布局，按当前筛选和用户选中设备分配槽位；轮播建议采用图中30秒默认值，允许暂停。对讲、核验或用户锁定某设备时不自动切走该设备。未选择或不足槽位显示空位，不制造不存在的摄像机。

流状态至少包括未开启、连接中、播放中、回传中断、不支持、无权限。断流最后画面加时间和明确覆盖提示；后台重连成功、收到新帧后才恢复实时标识。多路默认静音，用户主动选一路开声音，避免同时播放多个远端音频。

F08远程指导需先验证通信权限、设备能力和媒体访问授权，再调用现有厂商/Agora链路。抓拍区分设备拍照、媒体服务截帧或浏览器截图，资料记录真实来源；不能把屏幕截图冒充设备原始拍照。录制需明确是设备端、媒体服务端或浏览器端，只有支持并联调通过的方式可启用。

现有 [index.html](</E:/沉积岩/anquanchuandai/pc前端代码/melhat_pc-main/index.html:217>) 从远程地址加载 Agora SDK；新前台应将验证过的SDK版本纳入可控发布和网络方案，不依赖现场网络一定能访问外网。现有 `useAgoraRtc` 已有订阅和清理逻辑，但 Token 即将过期时只输出提示，应补短时凭据续期、失败恢复和UI状态。

播放器只为可见槽位创建，离开页面销毁监听/解码器；支持低码率副流时用于缩略图，不支持时不能假定节省了带宽。9路播放是否可用需按实际分辨率、码率、浏览器和值守机验证，画面布局支持不等于硬件保证9路高清流畅。

### 6.5 调度通信、广播与SOS

调度台复用单呼、群呼、组呼和TTS请求。组成员从后台协助组服务取得，人员可达终端实时解析并显示PC/APP/安全帽。安全带、手表是否能接受语音/广播由能力验证决定，不把所有穿戴设备当成对讲终端。

会话与参与者分别建状态。会话有创建、呼叫中、已建立、结束、失败；参与者有待邀请、邀请中、振铃、已加入、拒绝、超时、离线、退出。图中“群呼尚未全部接通”根据逐参与者结果生成，HTTP请求成功只表示已受理，不能把整组标成已接通。

通信服务放在应用级状态层，F03/F08/F11/F16所有“对讲”按钮操作同一会话。页面切换不重复呼叫，不在每页初始化一个竞争的麦克风会话。断网、拒绝麦克风权限、浏览器休眠、凭据过期、设备忙线均需可解释状态。

TTS广播包含目标校验、文本草稿、试听、发送确认、消息ID和目标回执。“试听”仅向当前用户播放，不下发到设备；没有试听服务时显示能力未提供，不把发送接口用作试听。草稿/发送中/已受理/部分成功/成功/失败分开；厂商只有受理回执时显示“已受理”，不声称每个成员已听到。

SOS使用现有安全帽上报能力建立协助会话，记录请求设备、发生时人员、定位来源与时间、协助组及参加者。加入按钮先进入连接中，收到链路/参与回执后再显示已加入；结束协助记录发起人、时间、原因与各端结果。结束通话不等于外部事件结案。

PDF F15明确是演练：为会话设置不可由普通请求随意修改的 `mode=DRILL`，使用独立演练编号和测试目标，所有关联记录继承模式。首页真实事件、真实统计与生产回传排除演练；真实SOS仍按正常事件处理，不能因为展示演练页而关闭真实SOS链路。

原安全帽SIP/Agora兼容、硬件自动接听、SOS长按3秒退出逐条真机验证。PC网页不能通过按钮“模拟证明”硬件已实现自动接听。紧急插入、强拆等PDF未明确的通信能力不默认新增。

### 6.6 实时定位、轨迹与围栏

一期人员位置优先来自其当前绑定且定位能力已验证的安全帽，与F03/F09/F10一致。安全带页显示“关联安全帽提供的人员位置”，不冒称安全带独立定位；手表位置能力未确认时不参与位置来源切换。

每个点记录设备、人员绑定区间、源时间、接收时间、坐标系、精度/定位方式（来源提供时）、数据质量。通信心跳新不等于位置新。展示位置时标明来源和时间；过期点可作为“最后已知位置”展示，但不算当前可靠位置。完全无有效点时只在列表提示，不随机放置人员标记。

保存原始上报坐标及其坐标系，业务计算与底图使用明确转换。现有 `coordTransform` 可以复用，但须核对真实地图瓦片的坐标系，避免重复转换。PDF没有室内楼层精度依据，不能声称可精确定位楼层或架空平台高度。

历史轨迹按人员/设备、时间、来源质量分段；数据间隔超出已配置阈值、换设备或无效点形成缺口，不能跨缺口画实线或生成插值点。时间轴保留缺口区间，播放到缺口显示“无可靠位置”；导出也保留缺口和原始时间。阈值依据协议正常上报频率制定，不能把图中8分钟缺口当通用阈值。

当前轨迹页面把坐标标准化后传给回放，需要改造成保留时间、质量及事件引用的分段结构。位置过期、电量和通信阈值由同一后端规则提供，各页面不能使用各自的定时器得出不同状态。

围栏保留原多边形/圆/矩形支持，视觉优先实现F06多边形编辑。增加厂站、适用人员/协助组、责任人、进入/离开条件、有效期和版本。保存前校验图形闭合、自交/空形状、坐标系和授权范围。

需要服务端在定位上报后执行人员适用范围及点位关系判断，使用可靠点、边界缓冲或持续时间抑制定位抖动，不能只靠浏览器地图判断进出。当前已见围栏CRUD和坐标管理，但不能据此认定完整进出规则引擎已经实现，应作为新增任务验证和补齐。

停用后停止新提醒，保留之前的判定和图形版本；删除采用停用/归档方式保留追溯。当前 [ElectronicFenceServiceImpl](</E:/沉积岩/anquanchuandai/后端代码/melhat_server-dev/ruoyi-system/src/main/java/com/ruoyi/helmet/service/impl/ElectronicFenceServiceImpl.java>) 更新/删除会删除旧坐标，且 `getAlarmCountByFenceId` 使用 `hatId` 过滤；即使已有增加 `fence_id` 的迁移，也须核查查询和所有写入路径，不能将新列存在视为逻辑已改好。旧记录缺少 fenceId 时保留未知关联，不把 hatId 当 fenceId 迁移。

### 6.7 现场资料与证据

复用 `file_record` 的文件身份、类型、地址及安全帽引用，新增拍摄时间、接收时间、上传来源、源设备、发生时人员、厂站、作业、事件和核验引用关系。照片、录像按PDF作为主标签；原录音资料保留在通信记录或资料扩展类型中，不因PDF未单列而丢失。

设备回传、远程抓拍、现场人工上传分别记录来源。上传先校验类型/大小和权限，文件成功存储后保存元数据，失败不得留下可被引用的“假成功”证据；重复提交使用文件ID和请求幂等处理。

证据与事件、作业、核验采用关联表，同一文件可在多处引用，不重复复制原文件。对正式核验使用的资料保留摘要校验值、版本和引用时间；更换资料产生新版本，避免核验提交后证据内容悄然变化。

查看、缩略图、下载、原图、视频播放都必须通过对象权限检查，可使用短时授权地址；不能只限制资料列表而暴露永久公网文件URL。历史访问按记录厂站与授权规则处理，不依赖设备今天调拨到了哪一厂站。

现有文件接口提供基础元数据和播放下载能力，其中上传记录接口不能替代完整文件上传存储闭环；新核验照片上传需要实际验证文件存储、失败清理、访问和引用。

## 7. 新前台工程与运行架构

### 7.1 建议技术和目录职责

沿用现有Vue 3 + Vite + Pinia + Vue Router + Element Plus + Axios，图表复用ECharts、地图复用OpenLayers、音视频复用现有FLV和Agora适配。新业务优先TypeScript明确契约；现有可复用JS模块可以逐步接入，无需先完成全量语言改写。

建议新工程位于 `pc前台代码/wearable-portal-web`，以下为规划目录，不是当前已创建结构：

| 目录职责 | 内容 |
| --- | --- |
| `src/layouts` | 深色统一壳、顶栏、侧栏、应用入口 |
| `src/views` | overview、people、work、video、dispatch、location、events、materials、statistics、login |
| `src/components/domain` | 人员装备、作业摘要、事件核验、状态和数据时间组件 |
| `src/services` | API客户端、旧接口适配、地图、媒体、RTC、事件订阅 |
| `src/stores` | auth、siteContext、monitorSnapshot、communication、verificationDraft |
| `src/contracts` | DTO、枚举、错误码、推送消息类型 |
| `src/theme` | PDF取样后的主题变量、组件覆盖和页面布局 |
| `src/assets` | 已确认品牌、设备图片、地图示意和演示素材 |
| `tests` | 关键领域状态、契约、跨页业务与视觉回归 |

两端各有独立环境配置、开发端口、构建产物和发布流程。推荐同域 `/portal/`、`/admin/`；新前台可采用history路由并配置服务器回退，原后台hash路由可先保留。开发代理指向同一后端，环境标识和地图/媒体/接口地址由配置提供，避免硬编码旧域名。

### 7.2 页面数据与跨页上下文

服务端聚合人员、装备、作业和事件，前端不为每行人员发十几个请求。概览、人员侧栏、作业详情分别提供聚合接口，但共享底层状态和统计定义。列表分页、资料分页、轨迹时间区间限制由后端执行，避免前端全量下载后分页。

跨页携带 `siteId/personId/deviceId/workId/eventId/timeRange` 中必要的查询上下文；切换目标页后重新鉴权和读取数据。不能把RTC Token、密码或外部接口凭据放进跳转URL。

厂站切换应撤销旧订阅、取消旧请求、清理旧数据，再加载新厂站快照；响应标识需带上下文，防止旧请求晚到覆盖新厂站页面。存在未保存核验草稿时提示保存/离开；存在进行中通话时按明确业务规则处理，不静默把同一会话移到另一厂站。

### 7.3 登录和实时消息

复用 `/login`、`/captchaImage`、`/getInfo`，为前台校验 `portal:access`。两端仍使用同一账号体系；菜单展示和服务端操作授权分别控制。按后台方案配置一次性会话交换实现两端切换，或在初期使用独立登录会话；任何免登方案都不能只靠前端复制URL中的长期Token。

建议建立“先取快照，后订阅增量，断线后重取快照”的机制。快照与增量之间用版本/游标对齐；去重乱序后应用更新。消息结构至少包含 `messageId/type/siteId/entityId/entityVersion/occurredAt/receivedAt/mode`，不能把旧消息覆盖为最新状态。

新增订阅主题包括设备状态、人员装备变更、位置更新、作业同步、事件新增/更新、核验版本、通信成员状态、广播回执。订阅身份与范围由服务端验证，普通客户端不能任意传厂站或用户ID订阅全厂消息。

现有WS已存在报警/SOS广播基础，但需补厂站/角色过滤、不同应用会话隔离，以及定位实时推送。多页面复用同一连接管理器；断线提示与后台自动恢复配合，不能在连接断开期间保留“实时正常”状态。暂不具备推送的业务可用受控轮询过渡，并展示更新时间。

### 7.4 媒体、文件和平台接入

业务后端负责身份、权限、设备解析、厂商适配和短时媒体凭据；视频/语音走既有设备平台/媒体服务链路。原始媒体可以沿用现有存储和接入部署，先验证容量及权限；对象存储等替换按需求另行决定，不将换存储作为UI建设前置条件。

一个业务后端代码库可以横向部署多个实例，但要补定时任务去重、跨实例推送和会话协调。新前台的聚合Controller只是同一后端中的接口层，当前不另建独立BFF服务。

### 8.3 安卓兼容与补充范围

安卓现有安全帽、围栏、报警、对讲和TTS接口在兼容期保持路径及基本响应。新后端严格授权后需给现有有效角色迁移必要权限，防止合法旧端业务全部被拒绝；同时不得因兼容而保留越权路径。

已有安卓仍可完成原功能；新三类设备、作业核验、前台同款会话状态若需要在安卓展示，属于后续对应功能增量。PDF审计示例中APP保存核验草稿需要新增安卓页面/接口调用，不能声称现有安卓自动支持。后端核验领域共用，避免日后另造移动端流程。

## 9. 三类设备接入及异常数据策略

| 设备 | 一期确定建设 | 条件能力 | 明确不推断的内容 |
| --- | --- | --- | --- |
| 安全帽 | 沿用真实同步、档案/领用、已有定位报警与媒体接口接入基础 | 视频、语音、拍照、录像、自动接听、SOS退出以现有设备真机验证为准 | 代码存在不代表每一型号支持所有能力 |
| 安全带 | 建档、领用、归还、人员关联、上报来源与通信状态 | 直连/通过网关、挂接、受力、电量等按协议确认 | 断连≠未挂接；在线≠穿戴合规；不能伪造安全带独立位置 |
| 手表 | 建档、领用、归还、人员关联、能力状态 | 通信、提醒、定位、传感按协议及联调结果启用 | 不默认增加健康诊断、心率/血氧、跌倒、摄像等功能 |

采用适配器把厂商SN、状态码、上报时间、设备能力与消息ID映射为平台标准模型。解析失败隔离记录并可追踪，不能把缺字段映射为“正常/0”。晚到数据进入历史，不覆盖更新的最新状态；时间明显异常标记质量问题。

通信状态需区分设备失联、网关失联、上游接口故障和本平台断网，向用户展示可验证的原因。能力未确认时仍保留PDF结构，显示“待协议确认/待联调/不支持”，相应按钮受控禁用，并提示具体原因。

## 10. 统计与追溯口径

所有指标必须带厂站/班次/日期/授权范围和 `asOf`，从服务端统一返回。例图8人、24件、23在线、3事件是演示样本，不是系统业务常量。

| 指标 | 建议定义 | 避免的误差 |
| --- | --- | --- |
| 当班人员 | 当前厂站有效班次名册中的不同personId数 | 不用用户总数或在线安全帽数代替 |
| 参与作业/待分配 | 当班名册中参与指定有效监护作业的人数去重；余下为待分配 | 同一人参加两项不能统计为两人 |
| 监护作业 | 当前范围/时间窗下符合本地有效监护状态的workId数 | 不把全部历史工作票计入 |
| 已领用装备 | 当前当班人员有效领用的deviceId去重数，按类型分组 | 不是人数乘3，也不包含全部库存 |
| 通信在线X/Y | 分母为上述已领用装备；分子为其中通信在线且状态来源有效的设备 | 在线不等于安全合规；库存在线另在后台统计 |
| 位置可查看 | 当班人员中有符合新鲜度/质量条件的授权位置数 | 历史点、无效点单列，不能充数 |
| 待认领/处理中/待现场核验 | 按本地跟进阶段互斥计数 | 不按“有核验草稿”自动改为已完成 |
| 待跟进/待核验事件总数 | 仍需跟进的真实事件去重数 | 排除演练和演示；持续断连仅一个事件 |
| 已核验 | 在查询口径下至少有一份已提交正式核验记录的事件数 | 排除草稿；另列已提交但仍需跟进数量 |
| 核验完成率 | 完成本地核验的真实事件数/需本地核验事件数 | 与“核验记录提交率”分开命名 |
| 回传成功 | 摘要与核验记录按各自回执计算 | 不把摘要成功合并成全部成功 |
| 外部结案 | 原安监系统返回已结案的事件数 | 本地核验和通话结束均不直接增加 |

F01核验进度图如按“有无正式核验记录”分段，已提交但仍跟进的事件必须只计入“已核验”一侧，并另显示跟进标识；F13顶部阶段计数按本地跟进阶段统计。两张图维度不同，应给出说明，不能把重叠维度相加为总事件数。

历史日期查询应基于当时班次、领用区间、状态记录及事件快照；没有历史在线状态时显示“历史数据不足”，不把今天在线状态写进昨天报表。图表点击穿透到使用相同筛选条件的明细，导出与页面数一致。

### 13.2 建议性能与稳定性验证基线

以下为待容量评审的建议目标，不是本次已测结果：

- 普通列表/详情在约定测试容量下，服务端P95响应目标不超过1秒；可操作首屏目标不超过3秒，媒体连接耗时单独统计。
- 设备消息到达本平台后，正常网络下页面增量更新目标不超过2秒；设备自身采样周期和厂商平台延迟另行记录，不承诺现场物理事件2秒内必达。
- 验证1+7、2×4、3×3在实际值守机、约定码率和分辨率下的播放与轮播；记录CPU、内存、网络、丢帧和首帧时间后确定正式上限。
- 至少覆盖完整值守班次的连续运行测试，检查播放器、地图、订阅、计时器和RTC资源是否增长；多次切页/切厂站/断网重连无重复会话和跨范围数据。
- 核验和领用等关键提交验证幂等、并发冲突和断网重试；事件持续断连验证防重；文件上传中断可恢复或明确失败。
- 历史轨迹、资料和导出按约定最大时间窗及数据量测试，避免无限范围查询阻塞在线监护。

## 14. 待确认项与落地建议

UI可按现有PDF直接形成详细设计和开发任务。真实生产闭环需要补齐：三类硬件协议和测试设备、地图源及坐标系统、厂站区域/人员/班次数据、工作票和安监接口、通信自动接听及退出行为、容量和资料保留周期、品牌原素材。

建议最先完成一条双端样板链路：后台建档并领用三类装备 → 前台人员与装备展示 → 安全带实际/模拟断连事件 → 查看关联安全帽视频及位置 → 认领和提交核验 → 后端记录回传回执 → 统计追溯穿透。模拟环境必须全程标示模拟；拿到协议后用同一契约替换真实适配器并重新验收。

这条样板链路同时检验两端共用后端是否正确、原功能是否能复用、三设备模型是否合理、PDF核心交互是否完整，再推广到全部页面和厂站。
