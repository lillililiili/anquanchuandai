# 智能穿戴设备平台：前台业务重组与开发方案 V2

进度修订日期：2026-09-20。状态：V2-0至V2-7前端演示已实现，领导评审待执行；正式设备能力、真实数据与业务权限仍待确认。原设备资料增补要求保留，阶段验证见记录11至19。

## 一、目标和设计依据

前台定位为值守、监护、核验和调度人员的业务工作端，不是设备后台换一套配色。首先回答“看哪里、查谁、跟什么作业、处理哪件事、联系谁、如何追溯”，再组织菜单。

原方案依据：新前台菜单、Mock 内存仓库，旧 PC 的 views、router、helmet/location API，以及 S0 复用矩阵和17页设计映射。原设计核对不等于全部旧接口安全审计。本次增补依据为《智能安全帽1.pdf》《设计需求评估-智能安全带项目_Ver100.pdf》《安全帽参数.docx》，资料定位和差异见第九节；产品介绍和需求评估不等于设备协议或真机验收。

PDF 位于 `E:/沉积岩/智能穿戴平台相关文档/前端页面-智能穿戴设备.pdf`。图片是设计参考，不是已确认的接口、权限、统计定义或真实设备能力。继续参考深蓝视觉、列表加摘要、监看分栏等构图，不机械保留导航及图片示例。

不为“与 PDF 不一样”而删改合理功能。人员、作业、事件仍有独立工作目标；真正需要调整的是工具之间重复的入口、上下文和操作归属。

## 二、建议导航：七个工作入口

| 一级入口 | 页面内组织 | 解决的问题 | 不承载什么 |
| --- | --- | --- | --- |
| 工作台 | 当班概况、我的待办、重点事件、常用入口 | 今天需要关注什么、先做哪件事 | 完整视频墙、完整统计报表 |
| 现场监看 | 位置视图、视频视图、轨迹回放、围栏 | 某个人/设备在哪里、现场什么情况 | 人员台账维护、独立通话系统 |
| 人员装备 | 当班人员、装备查询；人员/设备详情 | 谁在岗、领了什么、设备被谁使用 | 真实用户账号、设备厂家配置 |
| 作业监护 | 作业列表、作业监护详情 | 哪个作业、哪些人、哪些待跟进事项 | 工作票编制、许可和审批 |
| 事件处置 | 全部事件/我的待办、事件核验详情 | 哪件事谁负责、如何核验、后续怎样 | 把消息发送成功当作处置完成 |
| 调度协同 | 人员与协助组、通话、广播、会话记录；SOS详情 | 联系哪些人、每个人响应如何 | 班组/部门主数据维护 |
| 查询分析 | 现场资料、统计报表；关联记录跳转 | 发生过什么、证据在哪、如何汇总 | 第二套事件处理页或人员详情 |

七个菜单不是硬性上限：若评审确认视频是长期独立值守工位，可以恢复独立视频入口；本建议稿默认先合并，避免让使用者在两套监看上下文间反复找人。

顶栏保留厂站、当前身份、全局未结束协同提示和模拟标识。管理中心仍是外部入口；演示场景面板不算业务菜单。登录、人员详情、设备详情、作业详情、单路视频、核验详情、SOS详情都不是一级菜单。

| 现有入口 | 新归属 | 实质变化 |

## 三、前台与后台边界

| 业务 | 前台范围（本期均为模拟） | 后台/后续正式接入 |
| --- | --- | --- |
| 人员装备 | 当班查询、设备查询、日常领用归还及历史 | 人员档案、设备建档/同步/报废、厂家协议、组织授权 |
| 作业 | 查看来源作业、安排本地监护、开始/暂停/结束监护 | 工作票审批、许可、作业主数据及来源系统维护 |
| 围栏 | 查询、地图展示、模拟绘制/调整及版本演示 | 正式规则权限、生效审批、持久化和设备下发；默认不由普通值守员修改正式规则 |
| 资料 | 本地合成/用户选取资料的演示预览、关联和证据选择 | 真实上传、受控存储、下载鉴权、保留期限 |
| 事件 | 认领、转交、核验、记录、本地跟进完成 | 规则配置、真实告警源、审计及外部系统回传 |

领用归还是现场日常操作，可以放在前台；不因此新增完整后台台账。围栏编辑只作原型评审，正式权限边界需单独确认。

## 四、关键业务流程与页面行为

### 1. 日常值守

工作台查看本人待办及厂站概况 → 进入人员、作业或现场监看 → 查看同一对象的位置/视频 → 发现问题时进入对应事件。无事件关联证据时不自动创建真实告警，可在后期演示面板显式触发合成事件。

首页只做概要和直达入口，不复制完整地图编辑器、设备台账和核验表单。首轮就完成可用的简版工作台，不再长期把默认首页留为“功能建设中”。

### 2. 人员与装备

当班人员 → 人员详情 → 领用/归还 → 当前装备、空闲设备列表和历史同步更新。

新增装备查询标签及设备详情：按安全帽/安全带/手表、领用状态和关键词查询。区分正式人员ID、账号ID、设备ID、领用关系ID；同一设备同一时刻仅一个有效领用人，同一人同类装备最多一件。关系冲突必须展示和阻止新增领用，不能静默选择一条绑定。

人员详情复用原F03的头卡、三装备、历史和关联分区；设备详情补充“从设备找人”的入口。设备当前绑定不得补写过去事件和资料的人员归属。

离线、通信未知、数据过期只提醒，不阻止台账领用归还；领用关系未知或冲突必须禁止操作。型号和可选能力的补充不能改变这条已确认规则，也不改变同人同类最多一件的当前演示约束。

### 3. 作业监护

作业列表 → 来源摘要 → 参与人员与装备 → 监护记录 → 关联事件 → 本地监护结束。

来源作业许可只读；本地监护状态采用待开始、监护中、暂停、已结束。没有“开始监护＝工作票已许可”的联动。监护结束时提示仍未完成的事件，但不自动关闭事件。

### 4. 事件处置

待认领 → 认领后处理中 → 显式转现场核验 → 保存草稿/提交版本 → 负责人显式完成本地跟进。

- 草稿不改变跟进阶段；已提交版本不可编辑。
- 结论“无法确认”仍待现场核验，不能完成本地跟进。
- 其他有效结论提交后才允许负责人显式完成；回传成功不触发完成。
- 摘要回传、核验回传、原系统状态独立呈现；模拟回执说明未发送外部系统。
- 核验证据冻结资料ID、版本和摘要；事件时装备/位置与当前快照分开。
- “我的待办”只是同一事件列表的负责人筛选，不是第二套数据。

### 5. 调度与SOS

人员/作业/事件/单路视频上的联系入口 → 同一调度会话 → 分成员模拟响应 → 会话记录。SOS报警事实与后续协同会话分开：收到SOS不等于已建立通话；需要联系时复用统一会话模型，不新建另一套通话逻辑。

呼叫中、振铃、接通、拒接、超时、结束按成员记录；设备在线不等于可通话。切业务页保留全局会话提示；切厂站或注销前确认结束模拟会话，取消则保持原上下文。页面刷新按内存规则清空会话，明显提醒不持久保存。

### 6. 资料与追溯

视频演示抓拍/录像或本地选择文件 → 资料元数据及预览 → 关联人员/作业/事件 → 核验证据引用 → 统计明细跳转。

所有页面引用同一实体；查询分析的记录入口复用原详情，不复制处理表单。文件后续使用内存Blob与受控对象URL，刷新丢失；切换/移除时释放URL。不恢复IndexedDB，不上传到真实存储。

## 六、路由与Mock技术调整

保持Vue 3、JavaScript、Pinia、hash路由和当前依赖，不重建工程、不升级依赖。

延续已完成的导航重组，不大规模更改已有URL；未完成的详情随所属阶段新增：

- `/overview` 显示工作台。
- `/location?tab=live|tracks|fences` 与 `/video`、`/video/:deviceId` 均高亮现场监看；增加共享视图导航。
- `/personnel` 与人员详情保留；已新增 `/equipment`、`/equipment/:deviceId`，同属人员装备。
- `/supervision`、`/supervision/:workId` 承载作业监护。
- `/alarms`、`/alarms/:eventId/verification` 承载事件处置；UI名称可改，事件ID和现有查询不改。
- `/dispatch` 承载调度协同；SOS详情在V2-6按事件身份设计，不能要求尚未建立的会话ID才能查看报警。
- `/materials` 与 `/statistics` 均高亮查询分析，提供资料/统计页内导航。

新一级菜单默认落点依次为 `/overview`、`/location?tab=live`、`/personnel`、`/supervision`、`/alarms`、`/dispatch`、`/materials`。老链接仍可访问，返回地址必须经过白名单验证。页面内切换视图只带适用的厂站/对象筛选，不能把人员列表分页传给视频墙，也不能把当前人直接当历史轨迹归属。

Mock继续采用单页面生命周期内共享数据仓库；Pinia管理上下文和交互。写操作走统一业务服务更新实体及关系，不能只在组件里弹成功。刷新恢复种子、清空操作与场景；sessionStorage只保留模拟身份，演示页面明确说明。正式构建不导入Mock代码，不添加生产失败回退。

安全带可依据新增需求资料演示专属状态与事件，但必须标注“需求模拟，厂家协议待确认”，不能声称真实检测或控制已实现。按用户新增视觉要求，手表增加人形生命体征模拟面板，真实型号与能力仍待确认，不能把安全帽选配蓝牙手环当成独立手表规格。通信状态、数据新鲜度、领用状态、能力状态和业务异常独立表达，详见第九节。

### 9.4 待确认清单与推进方式

1. 安全帽型号及固件对应关系：DOCX未指定型号；宣传册低配功能清单与“全系列SOS”表述、临电/登高的型号范围存在不一致。保留两处依据，不自动选一条覆盖另一条。
2. 存储与配置差异：宣传册128GB与DOCX TF512GB可能对应不同机型/存储规格；电池表述单位亦需核实。暂不作为交互校验或上传上限依据。
3. 生命体征：宣传册心率/血氧与DOCX手环心率/体温/血压不是同一已确认配置；没有独立手表资料。暂不展示未经确认的真实传感能力。
4. 报告规则：心跳10秒及可配置值不等于离线阈值；DOCX低电提示规则不自动成为平台统一告警规则。姿态、跌落、静默、疲劳均需确认单位、状态码、阈值、生成主体及恢复机制。
5. 安全带：型号、钩/锁结构、低挂高用判断方式、自动锁止是否保留、SOS电话与平台告警关联均待确认。前端只展示明确标注的合成报告，不实现设备判断算法或控制。
6. 位置、隐私和资料：坐标规范、精度来源、隐私模式上报/恢复、拍摄时间、本地录像可访问性及授权方式待协议确认。

以上不阻塞纯前端原型：先以“需求模拟/配置未知/协议待确认”展示和评审；不确定字段可为空，阈值和设备命令不做。真实接入必须另行确认型号、协议、权限、安全规则和验证记录，不由本次模拟验收替代。

### 9.5 手表生命体征人形面板（用户新增视觉要求）

参考：[用户提供的看板照片](C:/Users/黄建凯/Desktop/5e25e33cd610fabd1fd90c057830eb26.jpg)左下角。采用其“蓝色发光人体轮廓、底部光环、两侧指标卡”的组织方式，不复制品牌、其他菜单、背景照片、人数及业务结论；人形必须实际可见，不能只用普通图标或指标表替代。

- **位置：** V2-1A先在人员独立详情增加完整“生命体征（模拟）”分区，装备详情的手表页复用同一组件；人员列表右侧仅显示紧凑摘要与详情入口。V2-5在作业人员详情复用，V2-7再在工作台增加紧凑入口/概况，不新增一级菜单。
- **画面：** 深蓝背景，中间完整正面人形、青蓝轮廓和适度发光，周围分布心率、血氧、体温、血压卡片。优先自绘本地SVG与CSS，不新增3D引擎或外部素材请求，不直接裁切照片作背景。连线是视觉索引，不表示传感器实际安装在胸腔或器官上。
- **个人与群体分开：** 人员详情展示所选人员的单次观测值和单位，不展示照片中的群体人数。工作台若统计有数据人数，须按授权名册及明确观测关联去重；不平均多人读数后放在单个人形上，不推算“健康人数”。
- **模拟范围：** 原型候选为心率（bpm）、血氧（%）、体温（℃）、血压（收缩压/舒张压，mmHg）；可提供固定合成读数供看效果，同时持续显示“模拟体征，非真实测量；手表能力待确认”。这些是界面需求，不是已确认设备字段，不设医疗阈值、健康评分或自动告警。
- **观测归属：** 每项独立保留来源设备、观测时间、接收时间、可用性、新鲜度及模拟标记。仅在明确模拟历史关系能证明测量时佩戴人时关联人员；领用/归还不能把原佩戴人的体征转给新人员，不虚构刚上报。
- **状态：** 没有手表、未接入、未知、过期、无权限、失败分别显示文字与占位“—”，仍可保留中性人形；无权限时不得展示读数或敏感来源。过期值可保留并显著注明“历史读数/已过期”，不能继续显示正常实时状态。
- **交互与可读性：** 以指标文字为主，人形为辅助；不得用绿色人体暗示健康、红色器官暗示诊断。颜色同时配文字/图标，正文对比度至少4.5:1。窄容器改为人形上、指标下，不压缩成不可读小字；不画假心电图、不用闪烁或脉冲模拟真实心跳，装饰动画支持减少动态效果。
