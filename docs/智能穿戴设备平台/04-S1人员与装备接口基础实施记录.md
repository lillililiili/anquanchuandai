## 四个接口

|接口|授权|默认数据行为|
|---|---|---|
|GET /api/portal/v1/context|有效登录|厂站[]，people能力UNKNOWN，SITE_SCOPE_NOT_INTEGRATED|
|GET /api/portal/v1/people|portal:person:read + 厂站范围|无授权厂站403；有范围但无名册/班次则明确NOT_INTEGRATED|
|GET /api/portal/v1/people/{personId}|portal:person:read + 厂站/对象范围|不存在或不可见404，不合成sys_user人员|
|GET /api/portal/v1/people/{personId}/equipment-history|read + history双权限及对象范围|无历史源明确NOT_INTEGRATED，不从当前绑定拼造流水|

源码位于后端ruoyi-admin模块的com.ruoyi.portal包。沿用Java 8，不改原Controller/Service及全局安全配置。

HTTP说明：Controller及其局部异常处理输出标准HTTP与业务码；现有全局认证过滤器在进入Controller前仍可能返回HTTP 200 / code 401。前台兼容两种401。本轮没有改变旧接口认证响应；完整运行安全过滤链的真实账号联调未完成，MockMvc测试不应被解释为真实JWT/Redis验证。

## 实际来源接入点

PortalSource按当前账号、厂站提供context、roster、person、equipment及history。默认实现不访问数据库/设备平台。未来接入真实来源时使用独立实现替代默认Bean；测试替身仅在测试代码创建，没有生产演示开关或万能账号。

实现真实来源前必须确认：

1. 人员主键、工号、person-account映射和权威名册；不能把全部登录账号或在线安全帽当当班人员。
2. 厂站授权与部门映射；通配操作权限不绕过厂站范围。context由来源按actor裁剪，服务再次校验查询对象范围。
3. 数据源需返回每请求独立DTO，不能共享可变缓存对象；按事件发生时关系验证历史归属。
4. 设备关系冲突应由来源在全局识别。当前聚合还检查同页重复设备归属；这不能替代跨页/跨班次的全局关系约束。
5. 当前基础服务在授权名册内排序/分页，再批量取当页装备；未进行生产大数据量压测。大名册接入时应把过滤/排序/分页下推到权威源，保持公共API不变。
6. sourceTime必须是有证据的UTC时间；默认不推导业务阈值。来源只有在已批准阈值下才可给出FRESH/STALE，缺源时间或未来时钟会降为UNKNOWN。
7. 安全带/手表在S1强制协议待确认：已领用不意味着在线、存在电量或可下发命令。协议到位后在后续阶段单独实现并验收。
8. 未给任何账号新增权限。现有*:*:*沿用若依操作权限语义，但依旧需要授权厂站。

## 前端接入与运行

在pc前台代码/wearable-portal-web执行npm run dev，端口5176。主页面#/personnel；详情#/personnel/{personId}?siteId=...。没有登录账号不能进入受保护页面，测试脚本里的密码不是可用账号。

业务入口在api/portal.js；字段/状态校验在utils/portal-contract.js；旧分页适配在utils/portal-adapters.js；context在store/context.js；查询取消与竞态控制在composables/usePortalQuery.js。旧分页适配函数不是新的人员来源，不能将适配后的设备total直接接到人员列表。

本轮已编译后端测试，但没有替换当前运行JAR。新增接口部署到现有后端后，默认真实页面显示未接入；没有部署时可能显示接口不存在/读取失败，不要开启demo或注册来绕过。
