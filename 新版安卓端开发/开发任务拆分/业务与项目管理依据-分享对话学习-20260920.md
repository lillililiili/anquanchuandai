# 融瓴智能穿戴平台业务与项目管理依据

整理日期：2026-09-20。

本文用于理解客户需求、控制项目范围、安排开发顺序和组织业务验收。依据用户提供的分享对话与本地需求资料整理，保留业务、产品、协作和交付逻辑，舍弃历史代码、命令、提交记录和具体开发操作。本次未实施开发，也未重新验证当前系统。

核心结论：在保留原安全帽接口与完整功能的基础上，扩展安全带、智能手表，把人员、装备、作业、区域、异常和责任人串成可用的现场监护流程。以实际业务结果判断交付，不能用效果图、页面数量或测试数量代替客户验收。

## 二 客户真正要买到的结果

客户需要的是面向电厂现场的智能穿戴管理平台，覆盖火电、新能源等场景。安全帽是原有基础，安全带和智能手表是明确新增范围，后续其他穿戴产品应能继续接入。

值守人员应能迅速回答：谁在作业、做什么、在哪里、戴了哪些装备、出了什么异常、由谁处理、处理到哪一步。设备管理员应能回答：设备属于哪个厂站、谁领走了、是否可用、何时归还或维修、历史如何追溯。

客户明确提出的三项改造约束：

| 客户要求 | 项目经理应守住的结果 |
| --- | --- |
| 与原硬件接口一致 | 老设备继续可用；原有呼叫、接听、挂断、SOS 和播报语义不能被界面改造改变 |
| 程序代码能用就用，少优化 | 优先承接既有能力；必要业务纠错仍要做，不为技术偏好启动整体重写 |
| 逻辑功能和界面着重优化 | 操作入口好找，页面之间有关联，状态可信，业务有人负责且能追溯 |

“原手册功能都要有，而且要超越”是明确要求。超越主要体现在多装备协同、人员与作业关联、异常核验、使用便利性与业务回流，不能靠堆菜单或增加效果图数量证明。

## 三 产品范围与边界

| 领域 | 本平台负责的内容 | 保持的外部边界 |
| --- | --- | --- |
| 人员 | 作业人员、班组、承包商归属、装备关系、监护责任 | 不接管完整人事、薪酬、培训体系 |
| 装备 | 建档、厂站分配、领用归还、换绑、维修停用、能力与使用历史 | 不扩为全厂生产设备资产管理 |
| 作业 | 关联任务或工作票摘要、人员、区域、时段、责任人与监护要求 | 不自行接管两票审批、许可和销票 |
| 事件 | 汇总异常、认领、通知、核验、转交、协助、记录与追溯 | 与客户明确正式结案权，避免两套系统各自结案 |
| 通信 | 围绕作业与事件的视频、对讲、群组协助、播报 | 不扩为通用会议或企业综合通信平台 |
| 空间 | 二维地图、必要区域及楼层、人员装备与事件位置 | 不扩为全厂工艺仿真或重型数字孪生工程 |
| 统计 | 装备可用性、监护覆盖、待处置情况、响应与处置时效 | 不接管发电效率、能耗与生产经营分析 |

客户已有工作票或安监系统时，重点实现“作业关联—现场监护—处置回流”。没有接口时，可用明确来源的录入或导入支持试点；导入任务不代表获得作业许可。

正式事件结案由谁负责必须按客户流程确定。若原安监系统主导处置，本平台记录核验并等待回执；若客户缺少该能力，可以由本平台承接约定范围内的处置。不能把某张效果图上的分工写成所有客户的固定规则。

数字空间服务于看清现场。楼层、位置来源、更新时间和可信程度必须有依据；不能凭海拔、漂亮模型或示意点位宣称精确定位。

新增需求先判断：是否服务穿戴或作业监护；是否影响发现、响应、处置、追溯；是否只需从已有系统读取信息。涉及新增业务体系、硬件能力或交付承诺时，再做范围决策。

## 四 业务对象与必须保持的关系

| 对象 | 业务含义与约束 |
| --- | --- |
| 厂站与区域 | 限定业务数据和责任范围；必要时包含建筑、楼层、平台、风机等位置上下文 |
| 人员 | 真实作业者，不等同平台账号；现场人员不必人人拥有登录账号 |
| 设备 | 每台设备独立建档，区分品类、型号和实际支持的能力 |
| 领用关系 | 谁在什么时段使用哪台设备；一人可同时使用帽、带、表，变更后保留历史 |
| 作业 | 把人员、装备、时间、区域与负责人关联起来；与外部工作票保持可追溯关系 |
| 事件 | 保留发生时的人员、设备、位置、作业与来源，之后换绑不能改写历史事实 |
| 通信与证据 | 服务具体人员、作业或事件；知道联系了谁、结果如何、材料属于哪件事 |

设备身份、产品能力、使用人员是三个问题。联网不能自动证明是谁佩戴；扫码编号不能替代设备来源验证；安全带不能仅作为安全帽档案里的一个附属字段。

展示和操作以实际能力为准。安全带没有对讲能力，就通过同人关联且可用的安全帽或手机联系；智能手表的定位、SOS 或其他指标必须依据实际型号资料和实测结果，不预先承诺。

同一人在空间视图中应有一致的人员位置解释。多设备位置冲突、室内外切换、位置过期或楼层不明时，应明确状态，不用任意一个点替代事实。事件发生位置与人员当前位置也要区分。

## 五 按完整流程组织产品

### 1 装备使用流程

设备建档 → 分配厂站 → 核实接入与状态 → 人员领用 → 使用与异常处理 → 归还或换绑 → 维护停用 → 查询历史。

领用入口必须明显。分享对话明确指出“管理中心 → 领用归还 → 办理领用”，设备档案可以提供关联入口。不能要求用户先猜中某个详情页才能完成常用业务。手机端是否办理管理操作按当前端的范围决定，不因为 PC 有功能就照搬。

验收要能说明谁办的、给了谁、哪台设备、时间和结果；防止重复领用、跨厂站误操作、维修停用设备被当作可用装备。具体例外规则由客户业务流程确认。

### 2 作业监护流程

取得作业信息 → 核对区域、时段、人员与监护责任 → 检查装备及待人工核验项 → 进行监护 → 跟踪异常 → 汇总监护记录。

作业详情应集中呈现任务或票据摘要、风险措施摘要、人员装备、位置视频和事件记录。用户不应为了了解一项作业在多个孤立页面间反复找人和设备。

任务延期、暂停、撤销、人员更换后，监护关联应跟随变化。平台的监护状态与客户正式作业许可状态分开；不把“装备正常”作为自动开工或复工依据。

### 3 异常处置流程

接收异常 → 找到人员、装备及相关作业 → 提醒责任人 → 认领或转交 → 联系现场并核验 → 留存处置说明与证据 → 按约定复核或回传 → 追溯。

责任交接未被接收前，不能出现事件无人负责。多人同时操作、重复通知、转交失败、回传失败等情况要有明确的归属与结果。是否强制复核、何时升级以及响应时限需按客户规则确定。

必须区分装备故障、疑似安全异常和人工核验结论。设备告警不是直接认定人员违章的结论；数据不足时应记录待核验。

### 4 SOS 与通信流程

SOS 到达 → 显著提醒 → 查看呼救人和可用位置 → 接听或加入协助 → 通信与现场协同 → 保存过程记录 → 按事件规则继续处置。

结束通话、退出协助与关闭事件是不同动作。接听按钮返回成功不等于真正建立通话。SOS 协助组必须有实际成员和参与结果；多条 SOS 不应被单条展示覆盖。

原有手机呼叫、帽端发起、群呼、同组 SOS 协助、帽端挂断、声音开关与画面放大均应回到原手册逐条核对。历史讨论中的 SIP 与声网版本差异作为兼容核对事项保留，不在本文决定实现路线。

### 5 视频值守流程

按人员、区域或作业找到画面 → 同时查看多个安全帽入口 → 中央重点画面轮播或手动选中 → 暂停、放大、声音控制 → 进入相关人员、作业或事件。

“所有安全帽镜头入口与中央轮播”是用户明确提出的需求。可同时播放路数、性能和硬件条件另行核实；有入口不代表所有流已在线。断流、静帧、样片和实时画面必须可辨识。

## 六 状态真实性是业务要求

| 容易混淆的状态 | 正确的业务解释 |
| --- | --- |
| 已领用与已在线 | 前者是资产关系，后者是通信状态 |
| 在线与正确佩戴 | 在线不能证明戴好、系好或挂点可靠 |
| 设备正常与作业安全 | 设备数据只能支持监护，不能代替现场判断和正式流程 |
| 无异常与数据缺失 | 没有收到数据时不能显示成“全部正常” |
| 服务端返回与硬件实测 | 后端也可能保存模拟数据，仍需说明来源 |
| 提交成功与设备执行成功 | 播报、呼叫等要区分受理、执行、回执、失败或超时 |
| 示意位置与实时位置 | 保留来源和时间，不能用固定点位冒充现场 |
| 结束通信与事件关闭 | 业务状态各自更新，不能互相替代 |

演示可以使用，但入口、数据和结果应明确标注。正式空数据不能自动补成样例；旧数据不能刷新时间后伪装成刚上报；未知告警不能任意归为 SOS。

## 七 用户角色与各端分工

| 使用者或端 | 主要任务 |
| --- | --- |
| 值长、调度、值守人员 | 查找人员，关注异常，接 SOS，看画面，联系与协调现场 |
| 安全监督员、现场监护人 | 查看相关作业与监护要求，核验异常，记录处理，跟踪未解决问题 |
| 班组长 | 联系本组人员，协调作业及装备，处理本组相关异常 |
| 设备管理员 | 设备建档、厂站分配、领还、维修停用与历史查询 |
| 平台管理员或运维 | 账号、角色、数据范围与接入配置，按授权使用 |
| PC 现场工作区 | 监护、人员装备联动、事件和通信；业务优先 |
| PC 管理中心 | 完整档案与管理操作，与现场工作区共享数据 |
| 安卓管理客户端 | 当前确认的现场、通讯、消息、我的及相关子页；适合现场查看、联络和处理 |

权限应控制能看哪些厂站、人员、设备以及能执行哪些操作。隐藏菜单不足以证明权限有效。切换厂站或账号后，列表、详情、告警和通信上下文必须一致。

安卓是手机管理客户端，不是安全帽固件。保持当前底部导航、Logo、按钮比例、已有功能和指定预览，不恢复亮暗切换，不把完整 PC 后台与三维场景搬上手机。

原手册的全文覆盖表仍需原文件逐条建立。对话已列出的功能只是最低核对线索，不能声称据此完成了全部覆盖核查。

## 九 客户系统对接的项目管理办法

目标是减少重复建任务、让每条异常找到责任人，并把处理记录送回客户工作流程。接口数量不作为竞争力或完成程度的直接指标。

| 参与方 | 需落实的责任 |
| --- | --- |
| 客户业务部门 | 明确作业流程、责任人、主处置系统、数据解释和验收场景 |
| 客户信息化及网安部门 | 确认授权、部署环境、网络路径和访问边界 |
| 原系统厂商或集成团队 | 提供接口资料、字段含义、测试条件、交付时间和维护安排 |
| 融瓴项目团队 | 提供自身对接能力，完成业务对应、同步反馈、异常处理和联合验证 |

输入重点：人员与组织、任务或票号、作业状态、区域、时段、成员、责任人及必要风险摘要。输出重点：装备关联、监护覆盖、异常、核验说明、处置记录和授权证据。

计划前核实接口是否存在、开放权归谁、是否另行收费、何时能用、升级后谁维护。不能把“客户愿意对接”当成“依赖已经就绪”。

同步失败应显示未同步或待核验。回传未收到确认时保留待回传状态，不替客户系统显示已经结案。不得默认可直接访问生产控制系统。

## 十 如何指挥后续开发

以下是本次整理后的管理建议，不是已下达的新开发任务，也没有改变既有编号、总览和进度。

### 先锁定验收基线

把原手册、客户后续意见、整体方案、指定预览与当前记录做成需求覆盖关系。每项注明来源、适用端、必需或待确认、现有证据、差距及验收场景。发生冲突时记录采用哪条要求及理由，不让开发人员自行猜测。

### 按业务闭环安排批次

| 顺序 | 交付目标 | 通过时应能展示的结果 |
| --- | --- | --- |
| 基线核对 | 保全旧安全帽能力与当前确认界面 | 原功能有去向，必要兼容事项及缺失资料有清单 |
| 基础业务 | 人员、厂站、帽带表档案与领用历史一致 | 能完成建档、分配、领还、查询；各端理解同一关系 |
| 现场监护 | 作业、人员、装备、区域和责任人贯通 | 从一项作业找到参与人员、状态与相关异常 |
| 事件通信 | 告警、SOS、联系、协助和核验形成闭环 | 能说明谁响应、通信结果、处理记录与未完成事项 |
| 业务对接 | 客户任务进入平台、记录回到指定系统 | 变更能同步，失败可辨识，责任与结案归属一致 |
| 现场交付 | 实际设备、客户环境和业务人员验收 | 原功能、新装备与端到端场景有现场证据及遗留说明 |

各批次是依赖顺序，不能据此推断全部从零开始。已有功能先核实后复用；接口和设备资料的准备应提前进行，不要等页面全部完成才发现依赖不可用。可先选一个具备资料与设备条件的真实作业场景，跑通后再扩大覆盖。

### 给开发人员的任务必须说清什么

每项任务包含：用户角色与问题、需求来源、适用端及入口、操作前提、业务规则、预期结果、异常与权限、依赖、验收场景与证据。技术实现由开发团队提出，项目经理检查其是否满足这些结果及兼容要求。

例如“完善 SOS 协助”不能只要求加按钮；应说明呼救来源、可见人员、认领与协助的关系、加入和退出结果、通话失败时怎样继续处置、多条 SOS 如何呈现，以及通过哪台真实设备验证。

### 状态与进度按证据记录

分开记录：需求已澄清、设计可审阅、页面或演示可用、系统业务已联调、真实设备已验证、客户已验收。一个功能可以处于不同维度的不同状态，不用单一“已完成”掩盖缺口。

周报或批次汇报重点回答：本次交付了哪个业务结果；谁做过验证；遗留什么；影响哪个目标；需要哪一方何时提供什么。不用代码行数、提交数、测试数或生成图片数代替进度。

减少重复确认。已明确的常规工作连续推进；涉及范围、费用、外部依赖、客户流程归属或确有歧义的决定时，准备具体选项后集中确认。避免反复“最后一轮审查”而没有可审阅结果。
